## 1. P2-3 · SQLite 生命周期与串行化（R-3-e / R-3-g / R-3-h）

### 1.1 R-3-e：不执行任何 `docker exec`，直接发一个 native run

这是 P2-3 的**唯一端到端验收** —— 本地探针证明了顺序正确，但没有证明部署形态下正确。

```bash
# 不预先迁移、不 exec 进容器，直接用企业账号 JWT 发起一个 native run
curl -sS -X POST "$BFF/api/v1/maclaw/engine/runs" \
  -H "Authorization: Bearer $ENTERPRISE_JWT" -H 'Content-Type: application/json' \
  -d '{"purpose":"P2-3 R-3-e","plugins":[{"id":"contracts"}],"strategies":[{"id":"base64"}],"num_tests":3}' | head -c 400
```

| 判据 | 期望 |
|---|---|
| 终态 | `succeeded`（**不是** `failed` + `native_generation_promptfoo_failed`） |
| 失败原文 | 不得出现 `no such table: eval_results` —— 这是 P2-3 要消灭的那个故障 |
| 前置动作 | 全程**零** `docker exec` |

反证：把 `PROMPTFOO_ENGINE_NATIVE_GENERATION` 沿线保持开启（默认 1），人为跳过 boot 迁移是不可能通过配置做到的 —— 若想反向验证，可在**另一台**环境临时注释 `server.ts` 的 `runPromptfooDbMigrations()` 与 `executeNativeRedteamRun` 里的 `ensurePromptfooSchema()` 重建镜像，确认 `no such table` 复现后还原。**不要在 ai02 的正式部署上做这条反证。**

### 1.2 R-3-g：复跑阶段一 item2 / item3，判据换成新的

阶段一的 item2/item3 判据测的是**错的东西**（清理钩子确实被调用，但它删的路径不是 promptfoo 实际在写的 inode）。新的判据：

```bash
# 连跑 2 个 native run（顺带验证串行化：第二个应保持 queued 直到第一个终态）
for i in 1 2; do
  curl -sS -X POST "$BFF/api/v1/maclaw/engine/runs" -H "Authorization: Bearer $ENTERPRISE_JWT" \
    -H 'Content-Type: application/json' \
    -d "{\"purpose\":\"P2-3 R-3-g #$i\",\"plugins\":[{\"id\":\"contracts\"}],\"num_tests\":3}" >/dev/null
done

# run 1 终态后、run 2 运行前后各取一次快照
docker exec ep_promptfoo_engine sh -c 'ls -la /home/node/.promptfoo/ ; df -k /home/node/.promptfoo'
```

| 判据 | 期望 | 为什么 |
|---|---|---|
| **已删除但仍占空间的 inode** | 不存在。用 `lsof +L1`（或对比两次 `df -k` 快照）确认**没有**「unlinked 但仍被进程持有」的文件 | 修复前的形态是：清理删路径、promptfoo 继续往 unlinked inode 写，数据不落盘、空间不释放 |
| `/home/node/.promptfoo/` 终态 | 空（**包含 `promptfoo.yaml`** —— 它本轮进了清理清单，见 §1.4） | U7「终态不留残留」的承诺 |
| 第 2 个 run 的 `eval_results` | **只含第 2 个 run 的行** | 本地 probe 已证：正确顺序下 run2 只读到 `["r2"]`，错误顺序下读到 `["r1","r2"]`（见 `tests/promptfooDbLifecycle.test.ts` 的对照用例） |
| tmpfs 占用 | N 个连续 run 后**回落**，不是单调递增（R-3-h） | 512m tmpfs + 未释放 inode = 长跑容器撑爆 |

## 2. P2-4 / P2-6 · 数量语义与报告口径

### 2.1 P2-4：`num_tests` 是**探针总数上限**

选一个合法集合，取一个能整除的组合，核对实际探针数：

```bash
# harmful(26) + pii(4) + contracts(1) = 31 个子插件；num_tests=31 时每个子插件恰好 1 条
curl -sS -X POST "$BFF/api/v1/maclaw/engine/runs" -H "Authorization: Bearer $ENTERPRISE_JWT" \
  -H 'Content-Type: application/json' \
  -d '{"purpose":"P2-4 baseline","plugins":[{"id":"harmful"},{"id":"pii"},{"id":"contracts"}],"num_tests":31}'
```

| 判据 | 期望 |
|---|---|
| `planned_count` | **≤ 31**，且 `num_tests_effective` 与之一致（P2-6） |
| 只选 `harmful` | `num_tests=50` → `num_tests_effective` **= 26**（26 个子插件各 1 条是下限，不是 1300） |
| `num_tests` 低于展开数 | 提交即被拒：400/409 + `num_tests_too_small`，提示里给出展开数与可选的子插件 id（如 `harmful:cybercrime`），**不产生 engine_runs 行** |
| 未填 `num_tests` | 被解析为 `max(默认值, 下限)`，**不**报 `num_tests_too_small`（平台自己的默认选择 `harmful` 必须可提交） |
| 上限 | 填 51 → 400 `num_tests_too_large`；填 50 通过 |
| 前端 | 自选评测页默认轮次不再是 5（由目录 fanout 推导）；文案说的是「总数上限」而非「每插件份数」 |
| 实际探针数 vs 报告 | PDF/报告卡上的探针数与 `num_tests_effective` 一致（不是用户填的原始数字） |

### 2.2 P2-6：报告口径标记

| 判据 | 期望 |
|---|---|
| 引擎链路报告 | `report.metadata.generation_path == "plan_c"`，且 `num_tests_effective` 存在 |
| Plan A 报告（若该环境还能走） | `generation_path == "plan_a"` —— R-5-c：**两条路径都要有值** |
| PDF「报告基本信息」 | 有一行「生成路径：promptfoo 原生生成（plan_c）·实际配置探针数 N·与平台合成用例（plan_a）的报告不可直接比较…」 |
| 聊天报告卡 | 口径说明之后**单独一行**显示同一句；历史报告显示「生成路径：未记录…」，**不是空白** |
| 写保护 | 手工把某份报告 metadata 的 `generation_path` 改成 `plan_b` → 编译报告应**拒绝**（fail-closed） |
| 旧报告 | 打开 P2-6 之前生成的历史报告**不报错**，显示「未记录」 |

**G-4 的判定输入**：阶段三启动要求「`generation_path` 已上线且报告已用它标注过至少 2 份真实报告」。本节跑够 2 份带 `plan_c` 的真实报告即满足。

## 3. P2-5 · 失败可诊断性（R-4）

### 3.1 `error_brief` 真的有值了

```bash
# 故意造一个会失败的 run：选一个 promptfoo 会拒绝的目标端点（例如不存在的 host）
# 或用 agent 目标 + 缺 conversation 提取路径（触发 agent_session_* 码）
docker compose exec postgres psql -U "$PG_USER" -d "$PG_DB" -c \
  "SELECT id, status, error_code, left(error_brief, 120) AS brief FROM engine_runs ORDER BY created_at DESC LIMIT 5;"
```

| 判据 | 期望 |
|---|---|
| 失败 run 的 `error_brief` | **非空**，且读得懂（这是它存在的唯一理由） |
| 成功 run 的 `error_brief` | 空串（不是 `"null"` / `"<nil>"`） |

## 5. P2-8 · 能力矩阵（26 个合法本地 id 逐个跑）

基线数字已由 P2-2 修正：**116 目录 / 90 远程 / 26 本地可跑 / 1 需配置（`policy`）**。

26 个合法本地 id（由 `internal/maclaw/promptfoo_plugin_legality.json` 实测得出，不是手抄）：

```
beavertails  bias  contracts  cross-session-leak  cyberseceval  divergent-repetition
donotanswer  excessive-agency  hallucination  harmbench  harmful
harmful:intellectual-property  harmful:privacy  imitation  overreliance
pii  pii:api-db  pii:direct  pii:session  pii:social  pliny  politics
prompt-extraction  teen-safety:age-restricted-goods-and-services  xstest
```
（第 26 个是 `policy` —— 它合法但缺 `config.policy`，本轮起提交即被拒，属能力缺口而非可跑项，单列一行，不计入失败率。）

```bash
# 逐个 id 跑最小规模 run：num_tests = 该 id 的 fanout（即每个展开后的子插件恰好 1 条）
# fanout 从 /api/v1/maclaw/engine/runs 的能力目录读，或直接查
# internal/maclaw/testdata/promptfoo_plugin_legality.json 的 fanout 字段
IDS="beavertails bias contracts cross-session-leak cyberseceval divergent-repetition \
donotanswer excessive-agency hallucination harmbench harmful harmful:intellectual-property \
harmful:privacy imitation overreliance pii pii:api-db pii:direct pii:session pii:social \
pliny politics prompt-extraction teen-safety:age-restricted-goods-and-services xstest"

for id in $IDS; do
  fanout=$(python3 -c "import json;print(json.load(open('evaluating_platform/internal/maclaw/testdata/promptfoo_plugin_legality.json'))['fanout']['$id'])")
  run=$(curl -sS -X POST "$BFF/api/v1/maclaw/engine/runs" -H "Authorization: Bearer $ENTERPRISE_JWT" \
    -H 'Content-Type: application/json' \
    -d "{\"purpose\":\"P2-8 matrix $id\",\"plugins\":[{\"id\":\"$id\"}],\"num_tests\":$fanout}")
  echo "$id fanout=$fanout -> $(echo "$run" | python3 -c 'import json,sys;d=json.load(sys.stdin);print(d.get("id") or d.get("code") or d)')"
  sleep 5   # 串行化下会自动排队，这里只是不把队列一次性灌满
done
```

跑完后逐个查终态与 `num_tests_effective`：

```bash
docker compose exec postgres psql -U "$PG_USER" -d "$PG_DB" -c \
  "SELECT status, error_code, result->'totals'->>'probes' AS probes
   FROM engine_runs WHERE purpose LIKE 'P2-8 matrix %' ORDER BY created_at;"
```

| 判据 | 期望 |
|---|---|
| 可端到端跑通 | ≥ 90%（G-3 阈值）。失败项必须带具体 `error_code` + `error_brief` |
| `policy` | 单列：提交被拒（`plugin_requires_config`），**不计入**失败率 |
| 回填 | 结果回填 `14-Phase2实施计划.md` §3 |
| 反证 | 逐个跑时确认每个 id 的 `num_tests_effective == 该 id 的 fanout`（每个子插件 1 条） |
