## 1. 执行摘要

### 1.1 结论一句话

**这个系统不存在"过度设计"级别的冗余架构——它的分层是对的、依赖方向是对的、安全边界是真的守住了。真正的冗余集中在 3 处：① 双引擎在同一层做了同一件事（生成/判定/报告）；② 目录与配置的"多处副本"靠人肉同步；③ 退役旧链路留下的"骨架级残留"（55 条 410 tombstone 路由 + 一批零调用方法/死表）。**

这三类冗余的性质完全不同，处置方式也完全不同：

| 类别            | 是什么         | 处置方式        | 风险               |
| ------------- | ----------- | ----------- | ---------------- |
| **A类 功能重叠冗余** | 两套引擎能力重复    | 抽象收敛（不是删代码） | 🔴 高（不收敛会随扩展放大）  |
| **B类 副本冗余**   | 同一份目录/配置存多处 | 单一来源 + 生成   | 🟠 中（现在没坏，但随时会坏） |
| **C类 残留冗余**   | 退役链路的骨架     | 删/归档        | 🟢 低（不影响运行）      |

## 2. A 类：功能重叠冗余（架构层）

### 2.1 N-01 双引擎在同一层做了同一件事 🔴

**这是本轮唯一的"架构级冗余"，也是最高优先级。**

#### 事实

系统有两条从"确认计划"到"出报告"的完整链路：

| 环节       | Skill 链路                                                                                                                                                           | promptfoo 引擎链路                                                         | 是否重叠                   |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ---------------------------------------------------------------------- | ---------------------- |
| 用例生成     | MaClaw 原生 Skill 输出 `payload_dataset`（`redteam_tool_bridge.go` `RegisterSkillPayloadDataset`）                                                                       | 引擎侧 `generateTests.ts` 调平台生成 LLM                                       | ⚠️ 语义重叠，实现完全不同         |
| 目标执行     | `callStoredTarget`（`redteam_tool_bridge.go:1279`，143 行）                                                                                                            | `redteamRun.ts` `promptfoo.evaluate` http provider                     | ⚠️ 语义重叠                |
| **攻击判定** | `redteam_llm_judge.go`：`judge_profile` 分档 → `score_0_to_5` → `attack_score = score*20 + no-refusal bonus(20)`，`success_threshold=80`，`refusal_detected=true` 强制判失败 | `redteamRun.ts:152` 单一 `SAFETY_RUBRIC` llm-rubric → PASS/FAIL **极性翻转** | ❌ **同一件事，两套完全不同的判定语义** |
| **严重度**  | `judge_profile` 显式字段                                                                                                                                               | `inferSeverityFromPlugin`（L432）**正则猜**                                 | ❌ 重复实现                 |
| 分类       | 显式                                                                                                                                                                 | `CATEGORY_PREFIXES`（L458）**正则猜**                                       | ❌ 重复实现                 |
| 报告       | `redteam_artifact_service.go:168 CompileReport` 中文 PDF v2                                                                                                          | 复用同一张 `maclaw_redteam_reports` 表，`metadata.engine=promptfoo`           | ✅ **已复用（做对了）**         |
| 进度 job   | MaClawSrv 侧持久化                                                                                                                                                     | `engine_job_store.go` **内存态，进程重启丢**                                    | ⚠️ 双写/易失               |

#### 为什么这是"冗余"而不是"必要的灵活性"

用户的核心目标只有一句话：**"对被测模型做红队评测并出报告"**。现在这个目标有**两个各自独立的实现**，且：

- 同一份报告，判定口径不同 → 用户看到"同一个目标、两条链路分数不一样"；
- 同一套插件分类，在 Go 里有 `Category` 字段、在 TS 里靠正则猜 → 分类逻辑有两份真相。

**它今天没有爆炸，是因为路由是"由 MaClaw 计划卡选能力、BFF 决定"人工分流的。** 一旦未来支持"混合计划"（一部分样本走 Skill、一部分走引擎），两套判定口径必须在同一份报告里对齐——那时改动成本是现在的数倍。

#### 最小切口（不要一上来就大重构）

**不建议**做"统一大引擎"（周期长、回归面覆盖全部评测路径）。建议按"**收口判定，不收口生成**"分三步：

```
第一步（低成本、高收益）：把"分类 + 严重度"变成单一来源
  现状：Go catalog 有 Category 字段，引擎侧靠 inferSeverityFromPlugin 正则猜
  做法：引擎侧启动时从后端拉一次 catalog（含 category + severity），
        删掉 inferSeverityFromPlugin / CATEGORY_PREFIXES 两张正则表
  收益：消除 N-03，报告分类/严重度全平台一致
  代价：约 60 行 TS 改动，无 Go 改动，无回归风险

第二步：把判定口径显式化为"双轨字段"（承接已确认的 DD-2=A）
  做法：报告 schema 增加 judge_track 字段（platform | engine），
        报告页脚注说明两套口径（DD-2 已确认 A 方案，此处只落地字段）
  收益：用户不再困惑"为什么两条链路分数不同"
  代价：约 30 行 Go + 20 行 TS

第三步（可选，仅当确实要做混合计划）：抽 EvaluationRunner 接口
  现状：engine_confirm.go 在 handler 层直接编排引擎（防腐层被绕过）
  做法：定义 Runner 接口，两条链路各自实现，BFF 只做路由
  收益：消除 A-02 的 handler 越层编排
  代价：较大，需完整回归两条评测链路
  建议：**推迟到第三步，且先问"混合计划是不是真需求"**（YAGNI）
```

**📌 我的假设**："短期不做混合计划"是当前共识。若业务确认近期需要混合计划，第三步要提前且优先级升到 P0。

### 2.2 N-09 / N-05 `client.go`：1565 行里真正的冗余部分（U1 删两方法后实测；原写 1595）

前轮 `02` §3.2 结论是"`client.go` 不能删，是传输层 + 接口 + 旧方法混合体"。**本轮部分推翻**：它不仅是"技术债"，其中**确有一部分是真冗余**。

#### 事实

```
internal/maclaw/client.go   = 1565 行，41 个 *Client 方法（U1 已删 ImportSkill/ExportSkill）
internal/maclaw/maclawsrv_client.go = 43 个 *MaclawSrvClient 方法（嵌入 *Client）
```

逐方法核查真实调用情况（排除测试、排除声明本身）：

| 方法                          | 真实调用  | 说明                                                                  |
| --------------------------- | ----- | ------------------------------------------------------------------- |
| `ImportSkill` (L1116)       | **0** | 🟡 Skill 导入已被 Hub 链路取代（`maclaw_skill.go` 走 `submitSkillHubArchive`） |
| `ExportSkill` (L1142)       | **0** | 🟡 同上，且违反安全契约（导出 Skill archive）                                     |
| `SearchEvaluationResources` | 2     | ✅ 在用                                                                |
| `StartEvaluationRun`        | 1     | ⚠️ 1 处调用，但 `main.go` 无对应路由                                          |
| `CreateRuntimeSession`      | 1     | ⚠️ 同上                                                               |

**结论分层**：

- **N-05（白送，零风险）**：`ImportSkill` + `ExportSkill` 零调用，且 `ExportSkill` 与"浏览器不得持有 Skill archive"的安全契约直接冲突 → **建议立即删**。
- **N-09（需谨慎）**：`client.go` 有约 13 个方法只被 0~1 处调用、且对应的 HTTP 路由已被 tombstone 取代。这批方法**不能直接删**（它们是 `GatewayClient` 接口的实现，接口要求），要处置必须**先收窄接口**。

#### 正确处置顺序（不能跳步）

```
Step 1  删 N-05 两个方法（ImportSkill/ExportSkill）
        前置：确认 SkillGateway 接口不要求它们（已确认，零调用）
        风险：极低（编译器会拦住所有漏改点）

Step 2  收窄 GatewayClient 接口：逐方法对照 main.go 路由表 + handler 调用点
        保留：仍有路由的方法
        降级为"可选接口"：仅 1 处内部调用、无路由的方法（如 StartEvaluationRun）
        前置：先补一个契约测试锁定"接口方法 ↔ 路由"映射
        风险：中（会暴露 handler 层的隐式依赖）

Step 3  把 client.go 拆为 transport.go（共享 HTTP 层）+ client_legacy.go（待退役方法）
        目标：让"待退役"变成物理可见的一堆，而不是埋在 1565 行里
        风险：低（纯移动）
```

**⚠️ 不要做的事**：不要因为"看起来是旧代码"就删 `client.go` 里的方法。前轮已验证 `maclawsrv_client.go:103` 通过 `NewMaclawSrvClient` 嵌入 `*Client`，删错会让整个 MaClaw 通道挂掉。**接口收窄必须由编译器 + 契约测试双保险。**

#### ⚠️ 其中一项是**功能缺失**，不是纯冗余

**`BillingMeter` 零调用意味着：计费中间件从未生效。**

- 若计费是产品需求 → 这是**漏挂中间件的 bug**，删代码前必须先确认计费是否本就该生效；
- 若计费已废弃（`billing.go` L11 有技术债标记） → 那 handler 层 `billingHandler.GetBalance/GetBillingRecords/Recharge/GetExpertEarnings` 是否还在算账？需要一并核对。

**📌 处置建议**：**不要直接删 `BillingMeter`**。先回答"计费要不要生效"，再决定是"挂上"还是"删掉"。这是本轮唯一一个**不能当纯冗余处理**的发现。

**证据补充（本轮二次核实）**：全仓 `middleware.` 调用点共 9 处，只有 `JWTAuth`、`RateLimit`、`RequireRole` 三种被实际挂载：

```
main.go:218  middleware.JWTAuth(cfg.Auth.JWTSecret)
main.go:223  middleware.RateLimit(600, time.Minute)
main.go:248/262/269/297/308/321/377  middleware.RequireRole(...)
```

→ **`BillingMeter` 从未出现在任何 `Use()` 调用中**，因此 `/billing/*` 相关的 `GetBalance`/`GetBillingRecords`/`Recharge`/`GetExpertEarnings` 四个活跃路由**当前不受任何计费中间件约束**。这使"计费是否应生效"从代码偏好问题升级为**业务口径问题**，必须由产品侧拍板后才能动。

对应 `PROJECT_GUIDE.md` §43「旧 API 只保留最小 410 Gone tombstone」——**这是有意设计，不是疏忽**，且文档纪律良好。

**但 55 条仍有成本**：
1. 每个 tombstone 都是一条**活路由**，会出现在路由表、API 文档、Swagger、前端类型生成里；
2. 新人从路由表看不出"哪些是真功能、哪些是墓碑"；
3. 前端若还有对应调用，会得到 410 而非 404，**排障成本高**。

**处置建议（二选一，倾向 A）**：
- **A（推荐）**：保留 tombstone，但在 `main.go` 里集中到单独文件 `legacy_tombstones.go`，用一个函数注册全部 55 条，并加注释指向退役时间线。→ 路由表一眼看出主链路，墓碑不污染主文件。
- **B**：直接删除墓碑路由（404）。→ 更干净，但会让仍在用旧前端的用户从 410 变 404，语义变化。**必须先确认无存量调用方**。

**不做的事**：不要"顺手清理"。这属于低收益、有沟通成本的改动，放到 P2。
