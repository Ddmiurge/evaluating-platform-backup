### 1.3 术语消歧：`jailbreak` 的两个命名空间（**D-2 与 D-5 引用此节**）

> **本节为 2026-10-13 补写。** 起因是用户提出的一句质疑：
> 「D-5 说 `jailbreak` 不认识，D-2 说 `jailbreak` 内部实现了，这不是有些矛盾么？」
> **用户是对的——同一个词被讲成了两件事。** 本节把两者拆开，并给出各自的位置与行号。

#### 现象

字符串 `jailbreak` 在平台里出现**两次**，分属两个**互不相干的命名空间**：

| 位置 | 身份 | 语义问题 | promptfoo 是否接受 |
|---|---|---|---|
| `internal/maclaw/promptfoo_plugin_catalog.go:274`<br>`p("jailbreak", "越狱对抗检测", "jailbreak", …)` | **插件位**（PLUGINS 选择器） | 生成什么攻击内容 | ❌ **不认识** → zod 拒 → **整 run 失败** |
| 策略侧（`promptfoo_strategy_catalog.go` / `nativeStrategyMap.ts`）<br>平台 id `jailbreak` → promptfoo `jailbreak` | **策略位**（STRATEGIES 选择器） | 怎么施加攻击 | ✅ **认识**，但内部升级为 `jailbreak:meta`，该实现要求云端 → 被四个 fail-closed **正确拦下** |

#### 根因（已核实）

平台对**策略**做了 `jailbreak:` 前缀的**去重映射**，但**插件目录没有做这层处理**：

- `promptfoo_plugin_catalog.go:155-172`（策略目录构建）注释明确写着：
  > Skip a native id the platform already surfaces under a different platform id.
  > `jailbreak:hydra` is `hydra`, `jailbreak:tree` is `iterative:tree` …
  > offering both would put the same attack technique in the selector twice under two names

- **但这段逻辑只作用于 `promptfooStrategyCatalogData`**，插件目录（`promptfooPluginCatalog`）
  是一条**独立的手写 var**，**没有对应的去重步骤**。
- 所以第 274 行的 `p("jailbreak", …)` 是**平台自起的名字**，与策略侧的 `jailbreak`
  **撞名纯属巧合**，不是有意复用。

#### 结论（明确写清，避免再次误判）

> **D-5 处置的是插件位（catalog 第 274 行），D-2 处置的是策略位（策略目录）。
> 两者处置不同对象，不构成矛盾。**
>
> - 插件位：`jailbreak` 不是合法 plugin id → **移出目录**（§3 / P0-2）
> - 策略位：`jailbreak` 是合法 strategy id，但依赖远程 → **记为已知能力边界**（§8 / D-2）

## 2. P0 清单（按严重度排序）

### P0-1 · `numTests` 语义错配 → 成本失控（最高优先）

#### 根因（实测）

`nativeRedteam.ts:795` 把平台 `num_tests` **原样**传给 promptfoo 的 `redteam.numTests`。
promptfoo 的 `RedteamConfigSchema`（`tables-BboCJNxW.js:2751-2754`）对每个 plugin 展开：

```js
plugins = redteamConfig.plugins.map(plugin => ({
  id: ...,
  numTests: plugin.numTests || options.numTests || redteamConfig?.numTests,  // ← 每个 plugin 都拿同一个值
}))
```

而 `harmful` / `bias` / `pii` 会在**同一层 zod 里被展开成子插件**（`RedteamPluginObjectSchema` 的 `.superRefine`）：

```
'pii'      → pii:api-db, pii:direct, pii:session, pii:social          （4 条）
'bias'     → bias:age, bias:disability, bias:gender, bias:race, politics, religion （6 条）
'harmful'  → 26 个 harmful:* 子插件                                  （26 条）
```

**实测 fanout 表（29 个 `local_only`，用真实 zod schema 求值）**：

| 平台 id | fanout | 平台 id | fanout |
|---|---|---|---|
| `harmful` | **26** | 其余 23 个合法 id | 1 |
| `bias` | **6** | | |
| `pii` | **4** | | |
| `prompt-injection` / `jailbreak` / `security-exploit` | **非法** | | |

#### 影响面（实测数字）

| 场景 | 探针数 |
|---|---|
| 表单默认值（`num_tests=5` + `plugins:['harmful']`） | **130** |
| 用户填 `num_tests=20` + 全选 26 个合法 id | **1180** |
| 用户填 `num_tests=50` + 全选 26 个合法 id | **2950** |
| 验收记录 item5b（`num_tests=10` + 4 插件） | **60**（不是 80，见 §0-A1） |

**放大系数 = Σ fanout**。用户填的数字是「每插件份数」，实际产出是 `数字 × Σfanout`。
最坏路径恰好是**表单默认值**（`harmful` = 26）。

> ⚠️ 三处上限不一致需一并修：BFF `engineRunMaxNumTests = 200`（`engine_run.go:36`）、
> 引擎 `Math.min(..., 50)`（`nativeRedteam.ts:795`）、前端 `max={50}`（`EngineEvalPage.tsx:331`）。
> **当前 BFF 允许 200，引擎静默夹到 50** —— 用户填 120 会得到 50 的语义，**且无任何提示**。这是独立的第二个缺陷。

#### 修复方案：语义对齐为「平台 = 总数」（**推荐**）

**理由**：平台 UI 写的是「用例数量」，用户的心智模型是「我要跑多少条」。
promptfoo 的语义是内部实现细节，不该泄漏到用户界面。而「保留每插件语义 + 改文案」
会把一个**财务风险**问题降级成**文案问题**——用户仍然无法预测成本。

**核心机制**：把「总数」**均摊**成每插件份数，写进**每个 plugin 自己的 `numTests`**，
而不是写进 `redteam.numTests`。

**实测验证了这条路径可行**（关键，因为 `RedteamPluginObjectSchema` 接受 per-plugin `numTests`）：

```
输入 redteam.numTests=50, plugins=[{id:'pii',numTests:3}, {id:'cross-session-leak',numTests:7}]
输出 → cross-session-leak:7, pii:api-db:3, pii:direct:3, pii:session:3, pii:social:3
```

**即 per-plugin `numTests` 会随子插件展开一起复制，且总数精确等于 3+3+3+3+7。**

##### 余数分配规则（必须明确，否则会出现「0 条插件」）

设平台总数 `N`（用户输入），平台选择的插件集合 `P`，`f(p)` = `p` 的 fanout。

**必须先算权重，而不是简单均摊。** 因为 `harmful` 展开成 26 条，而
`policy` 只有 1 条——若按「每插件 N/|P|」均摊，`harmful` 的每个子插件只有
`N/|P|/26` 条，**会算出 0**（而 `RedteamPluginObjectSchema` 的 `numTests` 是
`z.int().positive()`，**0 会被 zod 拒绝**）。

因此规则是：

```
1. 权重 w(p) = f(p)                        （fanout，= 展开后的子插件数）
2. 理想配额 q(p) = N × w(p) / Σw(q)         （Σ 对 P 中所有插件求和）
3. 向下取整 base(p) = floor(q(p))，至少为 1
   （若 Σbase > N，说明 N < |P|，此时按「先到先得」分配 1，其余给 0 —— 见下方边界）
4. 余数 r = N − Σ base(p)
5. 按小数部分 .q(p) − base(p) **从大到小**排序，每个插件 +1，直到 r 用完
   （同小数部分按 id 字典序，保证确定性 —— 反证测试需要这个性质）
```

**三条边界（必须写进实现与测试）**：

| 边界 | 行为 | 理由 |
|---|---|---|
| `N < Σw(p)`（总数小于 fanout 总和） | 允许部分子插件拿 1，但**必须让所有被选中的插件至少 1 条**——不能出现「某插件 0 条」。若 `N < |P|`（总数比插件数还小），则**按 id 字典序取前 N 个插件各 1 条，其余插件被显式拒绝并报错**（不静默丢弃，与 D4 的裁定一致） | zod 的 `numTests` 是 `positive()`，0 必被拒；而静默丢弃插件正是 §1.2 R-2 那类失败形状 |
| 余数并列 | 按 `id` 字典序 | 保证同一输入恒定产出，否则「同样的配置跑两次结果不同」会成为新的不可解释性来源 |
| fanout 未知（`file://` 自定义插件 / `custom:` 策略包） | `f(p) = 1` | 自定义插件不会展开。**实测 `RedteamPluginObjectSchema` 对 `file://` id 走 `z.string().superRefine`，不参与 `PLUGIN_COLLECTIONS` 展开** |

##### 对 U8 per-plugin rubric 的影响判断

**结论：不破坏，但会收窄一个已知的质量问题。**

- **不破坏**：U8 的 rubric 挂在 `graderGuidance`（`nativeRedteam.ts:389-406`），
  走的是 `withPluginJudgeRubrics()`，与 `numTests` 正交。均摊后每个插件仍有
  ≥1 条探针，`judge_sources` 仍然有值。**per-plugin rubric 的判定基础不变。**
- **会收窄**：`num_tests` 小于插件数时，某些插件只有 **1 条**判定样本。
  单样本的判定方差很大——但这**不是新引入的问题**：
  - 现状 `num_tests=10` + `harmful` 已经是「26 个子插件各 10 条」，
    用户以为的「10 条」和实际的「260 条」之间已经存在方差错配；
  - 均摊后 `num_tests=5` + 26 插件 = 每插件 1 条，**方差反而更小**
    （用户要的就是 5 条总量）。
- **对 U8 唯一真实的影响**：均摊后**同一插件的判定样本变少**。
  若某个插件只有 1 条且那条恰好通过，`judge_source` 会显示「已判定」但统计意义很弱。
  **处置**：不额外加代码；在报告里已有的 `plugin_stats` 显示实际条数即可
  （`reduceEvalToSafeResult` 已经按 plugin 统计，**无需新增字段**）。

**这一点必须写进 `14-Phase2实施计划.md` 的 §2.10.3**：
「报告里的判定基础必须与实际一致」在均摊后还多一条——**判定样本量也要一致**。

#### 反证方法

沿用 `15` §8 的纪律「每个新增护栏都做过反证」：

### P0-2 · 3 个非法 plugin id 在目录中可被选中

#### 根因（实测）

平台目录 `internal/maclaw/promptfoo_plugin_catalog.go` 有 119 个 plugin id。
U6 的 `promptfoo_remote_dep.json` 只标注了「是否需要远程生成」
（`catalog_marked_plugins`，90 项），**从未校验「这个 id 是否真的存在于 promptfoo」**。
29 个未被标注（`local_only`）的被当作「可本地生成」，但其中 **3 个根本不是合法的 plugin id**。

**实测（用 promptfoo 真实 zod schema 逐个求值）**：

| 平台 id | promptfoo 是否接受 | catalog 分类 | 后果 |
|---|---|---|---|
| **`prompt-injection`** | ❌ 拒绝 | `local_only` | 整 run 失败 |
| **`jailbreak`** | ❌ 拒绝（`jailbreak` 是**策略**不是插件） | `local_only` | 整 run 失败 |
| **`security-exploit`** | ❌ 拒绝 | `local_only` | 整 run 失败 |
| 其余 26 个 | ✅ 接受 | `local_only` | 正常 |

**promptfoo 的拒绝原文**（实测）：
```
Invalid plugin id "prompt-injection". Custom plugins must start with file://
or use a built-in plugin.
```

**「29 个可完整评测」这个数字因此是错的：真实值是 26。**
`internal/maclaw/promptfoo_remote_dep.go:283` 的
`remoteGenerationHintRecommends = {"harmful","jailbreak","pii","prompt-injection"}`
里有 **2 个非法 id**（`jailbreak` + `prompt-injection`）——
**用户被明确推荐了两个必然失败的插件**。这是 U6 闸门文案最严重的一处失真。

#### 三类处置（`prompt-injection` 的真实等价物到底是什么）

主理人问「`prompt-injection` 对应哪个真实插件」。**实测答案是：它不对应任何一个，而且不该被映射。**
实测发现**三种完全不同**的情况，必须分开处置：

| 类别 | 实测成员 | 处置 | 理由 |
|---|---|---|---|
| **① 平台自造，promptfoo 无对应** | `prompt-injection`、`security-exploit`、`jailbreak`(作为插件) | **移出目录** | promptfoo 有 `indirect-prompt-injection` 但它是 `REMOTE_ONLY`（远程依赖）；有 `shell-injection`/`sql-injection` 但它们**不在平台目录**。映射到任何一个等于**换一个用户没选的攻击面**，是静默改变评测语义 |
| **② promptfoo 有等价物且可本地跑，但平台漏进目录** | `shell-injection`、`sql-injection`、`debug-access`、`tool-discovery`、`bola`… | **加入目录**（独立批次） | 实测这些 `NOT_GATED`（不在 `remote_only` 也不在 `unaligned`），即真能本地生成。它们缺席是**目录不完整**，不是能力不可用 |
| **③ promptfoo 有等价物但远程依赖** | `indirect-prompt-injection`、`hijacking`、`system-prompt-override`、`agentic:memory-poisoning`、`ascii-smuggling` | **按 U6 现有机制置灰**（`remote_only`） | 已有机制，`gen_remote_dep.mjs` 会自动收录。**无需新代码** |

**对①的具体建议**：
- `prompt-injection` → **移出目录**。它的语义（「构造指令注入类攻击」）在当前
  本地集里**没有等价物**；最近的是 `indirect-prompt-injection`，但它远程依赖。
  若产品坚持要有「注入检测」，应**作为新插件入库**并接受它被 U6 置灰，
  而不是让用户选到一个必然失败的东西。
- `jailbreak`（作为插件）→ **移出目录**。它的语义已经是**策略**
  （`nativeStrategyMap.ts` 有 `jailbreak → jailbreak`，而 `jailbreak:meta` 因
  根因 B 被 fail-closed）。**插件位和策略位是两条不同的槽**，混在一张目录里
  是 U6 之前就有的分类错误。
- `security-exploit` → **移出目录**，但**其语义已被 ②覆盖**（`sql-injection` +
  `shell-injection` + `ssrf` 等）。建议按②入库，让用户选到真实可跑的东西。

#### 实测方法（**不靠猜**，这是 P0-2 的核心交付物）

新增 `scripts/gen_plugin_legality.mjs`，与 `gen_remote_dep.mjs` **同构**：

| 步骤 | 做法 | 关键点 |
|---|---|---|
| 1 | 读 `promptfoo/dist/src/index.js` 的 `from "./tables-XXXX.js"` import 语句，取出 `RedteamConfigSchema` 等 zod schema 的**别名 → 导出名 → chunk 文件名**映射 | **按语义名解析，不按 minified 导出名、不按内容哈希文件名**（`gen_remote_dep.mjs:38-51` 已确立这条纪律，本次沿用） |
| 2 | `import` 该 chunk，取 `RedteamConfigSchema`（实测对应导出名 `Y`） | 已实测可用 |
| 3 | 读平台目录的 119 个 id（复用 `gen_remote_dep.mjs` 的 `readCatalogPluginIds()` 形状解析） | 不手写 |
| 4 | 对每个 id 求值 `schema.safeParse({numTests:1, plugins:[id], strategies:[], purpose:'x'})` | **这是「promptfoo 真正接受」的定义**，比读源码字面量可靠 |
| 5 | 对**通过**的 id 再取 `result.data.plugins.length` → 这就是 **fanout**（同时解决 P0-1 的权重数据源） | 一份数据两处用 |
| 6 | 输出 `promptfoo_plugin_legality.json`：`{ promptfoo_version, invalid: {...}, fanout: {...} }` | CI 断言 |

**产出同时解决三件事**：
① 3 个非法 id 的清单 → P0-2；
② 每个 id 的 fanout → P0-1 的均摊权重；
③ **一条 promptfoo 升级即漂移的护栏**（与 U6 现有护栏同形状）。

#### 历史数据处理

实测确认：`engine_runs.plugins` 是 JSONB，非法 id 已经**真的落进库里**了。

| 处置 | 判断 |

### P0-3 · 根因 A：库模式不迁移 + 清理钩子与 memoize 连接冲突

#### 根因（实测，且比主理人描述的更深）

**表层**（已核实）：promptfoo 的 `checkRedteamProbeLimit()`（`index.js:17227`，在
`doGenerateRedteamInternal` 最开头）会查 `eval_results`，而库模式**不自动迁移**。
`runDbMigrations()` 只在 `doEval({write:true})` 内被调用（`index.js:18333`），
而那是**生成之后**的 scan 阶段——**顺序正好反了**。测试夹具 `u9PromptfooHome.ts`
预先迁移，**生产代码没有**，这就是契约漂移。

**深层（本轮新发现，主理人的手工绕过不充分）**：

`getDb()`（`tables-BboCJNxW.js:3818-3829`）**memoize 连接**：
```js
async function getDb() {
  if (dbInstance) return dbInstance;   // ← 进程生命周期内第一次调用就固定了文件
  ...
}
```
而清理钩子 `cleanupPromptfooRunArtifacts()` 每次 run 终态都 `rm` 掉 `promptfoo.db`。

**实测（`p2dbmemo2` 探针，用真实 `getDb()` + 真实 migrate）**：

```
run1  通过 memoized 连接写入 marker 'r1'
清理  rm promptfoo.db                       （路径上文件消失）
再迁移 在路径上创建一个【新的空库】
run2  通过同一个 memoized 连接写入 marker 'r2'
      → 通过 promptfoo 连接读到 ["r1","r2"]   ← 写进了已被 unlink 的 inode！
      → 通过新开连接读路径上的库：报错 no such table   ← 路径上的库是另一个
```

**所以「每个 run 前手工预迁移一次」这个绕过是不充分的**：
迁移创建的是一个**新的**文件，而 promptfoo 继续往**已删除的 inode** 里写。
后果有两层：
1. **数据不落盘** → `loadEvalResults()` 通过同一个连接读，能读到（所以 U8 侥幸没坏）；
2. **但清理钩子失去了意义**——它删的是路径，而真正被写入的 inode 是 unlink 的，
   **磁盘空间在进程存活期内不会被释放**。长跑容器 + 大 fanout = tmpfs 撑爆。
   且 `17` 实测 item3 的「清理失败降级」在这条路径下**测不到真实效果**。

#### 修复方案与执行顺序（本节是主理人明确要求设计的）

**正确顺序（已实测证明，见 `p2dbmemo3`）**：

```
① boot（容器启动，promptoo import 之后、接单之前）
     → resolvePromptfooDbPath()
     → runPromptfooDbMigrations()            幂等
② 每个 native run 的 native 路径初始化（executeNativeRedteamRun 开头）
     → ensurePromptfooSchema()               幂等：库不存在或缺表则迁移
③ 每个 native run 的终态清理（onTerminal 钩子内，删文件【之前】）
     → closePromptfooDbIfOpen()              ← 关键：先关连接，让 memoize 失效
④ 然后才 rm promptfoo.db / -wal / -shm / evalLastWritten / cache / promptfoo.yaml
```

**实测输出**（`p2dbmemo3`，用真实 `getDb()` + `closeDbIfOpen()` + 真实 migrate）：
```
[run1] via promptfoo conn: ["r1"]
[after run1] fresh conn at path: ["r1"]
terminal: closeDbIfOpen -> rm, exists = false
[run2] via promptfoo conn: ["r2"]        ← 只剩 r2，r1 真的消失了
[after run2] fresh conn at path: ["r2"]  ← 路径上的库和连接看到的是同一个
```
**这同时证明了「阅后即焚」在修复后是真正成立的**——现状下 r1 其实还留在内存里的 inode 中。

##### 调用入口与时机（主理人明确要求核实）

| 问题 | 核实结果 |
|---|---|
| **正确的迁移入口？** | promptfoo **没有导出**任何迁移 API。实测：`import('promptfoo')` 的 88 个顶层导出 + `default` 的 5 个 key 里，**没有任何 `migrate`/`getDb`/`closeDbIfOpen`**（`redteam` 下的 `Extractors/Graders/Plugins/Strategies/Base/generate/run` 也没有）。所以**必须自己调 drizzle**——这正是 `u9PromptfooHome.ts` 做的事，**不是绕过，是唯一可行路径** |
| **依赖可用吗？** | ✅ `drizzle-orm@0.45.2` + `@libsql/client@0.17.4` 已在 `node_modules`（promptfoo 的直接依赖）。⚠️ **它们不在 `promptfoo_engine/package.json` 的 `dependencies` 里**——生产代码 import 它们属于**依赖 phantom**（靠 npm 扁平化侥幸可用）。**必须显式加进 `dependencies` 并锁版本** |
| **migrations 路径怎么解析？** | **不要用 `getDirectory()` 那套逻辑**（`resolveMigrationsFolder()` 是内部函数，且它按 `PROMPTFOO_CONFIG_DIR` 反推，逻辑脆弱）。实测用 `import.meta.resolve('promptfoo')` 拿到 `dist/src/index.js`，去掉 `/dist/src/index.js` 拼 `/dist/drizzle` → 存在且迁移成功（实测建出 `eval_results` + `evals` 两张表） |

##### 为什么必须改清理钩子的形状（不能只在前面加迁移）

| 方案 | 够不够 | 理由 |
|---|---|---|
| 只在 run 前迁移 | ❌ **不够** | memoize 连接仍指向 unlinked inode。数据不落盘、磁盘不释放、清理失效 |
| 只在 run 前迁移 + 迁移前先 close | ✅ 够 | close 让 memoize 失效，下次 `getDb()` 重新开连接指向路径上的新库。**这是最小改动** |
| 迁移放 boot，close 放终态清理 | ✅ **推荐** | 职责分离：**迁移是「准备」**（一次性），**close 是「拆卸」**（每 run）。终态清理本来就该关连接——它已经在删文件了，先关后删是同一条生命周期的正确顺序 |
| 干脆不删 db，改成每次 run 前 truncate | ❌ 不推荐 | 改变了 U7「阅后即焚」的核心承诺，且 `:834` 附近多处逻辑依赖「文件不存在」 |

**推荐落地**：新增 `src/runner/promptfooDbLifecycle.ts`，导出
`resolvePromptfooDbPath()` / `runPromptfooDbMigrations()` / `ensurePromptfooSchema()` /
`closePromptfooDbIfOpen()`；在 `server.ts` boot 与 `executeNativeRedteamRun` 入口接线；
在 `promptfooStateCleanup.ts` 的删除动作**之前**插入 close。

| 位置 | 状态 |

### 3.4 `prompt-injection` 的真实等价物 —— 分三类回答

主理人问的是「真实等价物是什么」。**实测答案：分三类，且第一类没有等价物。**

| 候选 | 在 promptfoo 0.123.0 | 在平台目录 | U6 分类 | 能否本地跑 | 结论 |
|---|---|---|---|---|---|
| `direct-agent-harm` | ❌ **不存在**（157 个插件全表无此 id） | — | — | — | **主理人给的这个候选是错的** |
| `shell-injection` | ✅ 存在 | ❌ 不在目录 | `NOT_GATED` | ✅ 能 | **②类：漏进目录，建议加入** |
| `sql-injection` | ✅ 存在 | ❌ 不在目录 | `NOT_GATED` | ✅ 能 | **②类：建议加入** |
| `indirect-prompt-injection` | ✅ 存在 | ✅ 在目录 | **`remote_only`** | ❌ 远程 | **③类：已被 U6 正确置灰** |
| `hijacking` / `system-prompt-override` / `ascii-smuggling` / `agentic:memory-poisoning` | ✅ 存在 | ✅ 在目录 | **`remote_only`** | ❌ 远程 | ③类，已正确处理 |
| `ssrf` / `bola` / `bfla` / `cca` | ✅ 存在 | ❌ 不在目录 | **`remote_only`** | ❌ 远程 | 若要加②需同时进目录**和** U6 清单 |

**结论（这是主理人问题的直接答案）**：
> **`prompt-injection` 在本地可跑集合里没有等价物。**
> 最接近的 `indirect-prompt-injection` 是远程依赖，当前环境（四个 fail-closed 开关）
> **永远跑不了**。因此正确处置是**移出目录**，而不是映射——
> 映射到 `indirect-prompt-injection` 会让用户点进去后撞 U6 闸门（另一个失败形状），
> 映射到 `hijacking`/`system-prompt-override` 同理（都 `remote_only`）。
> **唯一能真正满足这个语义的做法是把 `sql-injection`/`shell-injection` 作为新插件入库**
> （它们 `NOT_GATED`，真能本地跑），但那是**另一个攻击面**，需要产品同意，
> 不应挂在「修一个 bug」的批次里。

### 3.5 三者性质并不相同（分类表）

> A3 说「实测 3 处非法：`prompt-injection`、`jailbreak`、`security-exploit`」——
> **数字正确，但三者的性质并不完全相同**，混在一张清单里处置会丢掉关键差异。

| id | promptfoo 是否认识（plugin 位） | 性质 | 说明 | 处置 |
|---|---|---|---|---|
| `prompt-injection` | ❌ | **平台自造，且本地无等价物** | 最接近的 `indirect-prompt-injection` 实测为 `remote_only`（`promptfoo_remote_dep.json`），四个 fail-closed 下**永远跑不了**。⚠️ 但它在**策略位**是合法的废弃别名（等价 `jailbreak-templates`），见 §1.3 | 移出插件目录 |
| `security-exploit` | ❌ | **平台自造** | promptfoo 把这个意图拆成 `sql-injection` / `shell-injection` / `ssrf`。前两者 `NOT_GATED`（真能本地跑），`ssrf` 是 `remote_only` | 移出插件目录；其语义由 ②类（`sql-injection`/`shell-injection` 入库）承接 |
| **`jailbreak`（仅插件位）** | ❌ | **平台自造，且该词在策略位另有其人且合法** | 策略位 `jailbreak` 合法（promptfoo 旧别名 → 等价 `jailbreak:meta`），平台策略目录**已经识别为废弃别名并给出推荐替代**（`promptfoo_strategy_catalog.go:355-365`）。**插件侧没有做同一件事** → **见 §1.3 术语消歧** | 移出插件目录**并改名**（见 §3.5.1） |

**一句话归纳**：
> `prompt-injection` 与 `security-exploit` 是「**造了个上游没有的东西**」；
> `jailbreak`（插件位）是「**造了个名字，恰好撞上了上游另一个命名空间里合法的 id**」。
> **前者只需删除，后者还需改名**——因为删除之后，用户仍然需要「越狱对抗检测」这个能力入口。

### 3.5.1 顺带把这个易撞名 id 改名（**用户已认可**）

## 5. 根因 A 的自动迁移设计（完整版）

> 主理人问的三点：① 正确的调用入口与时机 ② 迁移与清理钩子的执行顺序
> ③ 不能出现「迁移完立刻被清」或「清理完没迁移」。**三点全部已实测回答。**

### 5.1 状态机

```
容器 boot
  └─ server.ts 启动
       ├─ assertSandboxInvariants()            （现有，不动）
       ├─ resolvePromptfooDbPath()             【新增】与 promptfoo 同规则解析
       ├─ runPromptfooDbMigrations()           【新增】幂等；失败则**拒绝启动**（fail-closed）
       └─ 挂载 onTerminal 清理钩子（现有条件）

每个 native run
  ├─ executeNativeRedteamRun 入口
  │    └─ ensurePromptfooSchema()              【新增】幂等；带进程级锁
  ├─ ... 生成 / 执行 / 判定 ...
  └─ 终态
       └─ cleanupTerminal
            ├─ workdir rm -rf                  （现有）
            └─ onTerminal → promptfooStateCleanup
                 ├─ closePromptfooDbIfOpen()   【新增】必须 FIRST
                 ├─ rm db / -wal / -shm / evalLastWritten / cache / promptfoo.yaml
                 └─ （可选）ensurePromptfooSchema()  ← 见 5.3 的取舍
```

### 5.2 「不能出现迁移完立刻被清 / 清理完没迁移」

| 担心 | 为什么不会发生 |
|---|---|
| **迁移完立刻被清** | 迁移在 run **开始前**，清理在 run **终态**。中间隔着整个 run 的执行。唯一风险是「run 还没开始就被清理」——但清理只挂在 `onTerminal` 上，只在 run 终态触发 |
| **清理完没迁移** | `ensurePromptfooSchema()` 在每个 run 入口无条件调用（幂等 + 锁），不依赖「上一个 run 清理过没有」 |
| **并发**：worker A 在 close，worker B 在 migrate | `dbLifecycleLock`（模块级 promise 串行化）把 close/migrate/清理三者纳入同一临界区。**这是必须的**——`TaskManager` 是单进程多 worker |
| **close 之后立刻有别的 run 已经在跑** | `onTerminal` 是在 `runSafe` 的 `finally` 里调用的，此时该 worker 已经离开 `execute`。但**另一个 worker 可能正在跑**。→ 因此 close+删文件+下次 migrate **必须整体在锁内**，且**锁的粒度是「db 生命周期」而非「单 run」**。⚠️ **这里有一个真实的并发风险：worker A 清理时 worker B 正在往 db 写**。**处置见 5.4** |

### 5.3 一个必须承认的残留问题

**worker B 正在运行时，worker A 的终态清理会把 B 的数据一起删掉。**

这是**现状就存在**的（`cleanupPromptfooRunArtifacts` 删的是全局路径
`~/.promptfoo/promptfoo.db`，不是 per-run 的），**阶段二不修它**——

### 6.1 · S-1 的独立核实：为什么 `promptfoo.yaml` 该被删

`promptfooStateCleanup.ts:39-45` 的注释明确把 `promptfoo.yaml` 列为**不删**的对象：

> `~/.promptfoo` can hold a developer's cloud login (`auth.json`) and a
> hand-written `promptfoo.yaml`; neither is ours to delete

**实测结论：这个注释的前提在容器里不成立。**

| 事实 | 依据 |
|---|---|
| `promptfoo.yaml` 是 **promptfoo 自己的全局配置文件**，不是手写的 | `dist/src/cloud-*.js:9-25`（`globalConfig/globalConfig.ts`）：`readGlobalConfig()` / `writeGlobalConfig()` 读写 `~/.promptfoo/promptfoo.yaml` |
| 它的内容是**一个随机 UUID**（匿名安装 id） | 同上：`let globalConfig = { id: crypto.randomUUID() }`，且 `if (!globalConfig?.id)` 时会补一个并写回 |
| 41 字节 ≈ 一个 UUID 的 YAML | 与 `17` 实测的「41 字节残留」吻合 |
| **引擎从不写它** | 引擎的 per-run 配置写到 `workdir/redteam-config.yaml`（`nativeRedteam.ts:117` `CONFIG_FILE_NAME`，`:832`）。**不是同一个文件** |

**所以「不删 hand-written promptfoo.yaml」这条保护是对的，但它保护的是一个在容器里
永远不存在的文件**（容器里没人手写 promptfoo 配置）。
真实后果是：
- 每次 run 留下一个 41 字节的 UUID → **无安全影响**（不含任何载荷）
- 但它**会持续存在**，与 U7「终态不留残留」的整体承诺不一致
- 且 `17` 实测 item2 把它记为「例外」，是因为清理清单里没有它

**处置**：
1. 加进 `RUN_ARTIFACTS`（`promptfooStateCleanup.ts:70`）。
2. **必须改注释**：把「hand-written `promptfoo.yaml`」这条理由删掉，替换为实测事实
   （「`promptfoo.yaml` 是 promptfoo 的匿名安装 id，容器内无人手写，删除安全」）。
   **代码与注释矛盾会让下一个人重新做出错误的判断**——这正是本轮要避免的。
3. ⚠️ 保留 `auth.json` 的不删保护（那条**是**对的——云登录不是我们的）。
