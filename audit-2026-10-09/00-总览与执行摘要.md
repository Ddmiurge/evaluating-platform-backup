## TL;DR

**系统技术上可运行、可演示、安全边界基本守住；真正的风险不在代码质量，而在"工程治理失控"。** 最致命的是：**整个 promptfoo 引擎子系统与 2026-09~10 的服务器迭代全部未纳入版本控制，本机磁盘是唯一副本**；且工作区存在**未被 `.gitignore` 覆盖的明文密钥与数据库转储**（一旦 `git add -A` 推送即泄漏）。建议先"隔离敏感 → 开备份分支快照提交 → 建 CI"，再进入架构加固与《用户目标（聊天式自动生成方案 / 类 promptfoo 插件策略扩展 / Agent 红队）》的能力建设。

## 3. 需求与交互流程确认（要点）

- **一句话定位**：面向企业的"大模型/智能体红队安全评测平台"——以**对话式 AI 自动生成红队测试方案**为主入口，用**可扩展的插件 × 策略攻击矩阵**对用户自有 **LLM / Agent** 做并发安全测试，产出**中文 PDF 安全评估报告**。
- **主链路（保持不变）**：聊天描述需求 → MaClaw 追问(`ask_user`) → `plan_confirm` 执行确认卡 → 用户确认(可覆盖 `test_count`，携带 `plan_message_id`) → 进度卡(`planned_count`/`executed_count`/`current_stage`/`duration_ms`) → 完成卡 + PDF 报告。
- **辅助入口**：`/enterprise/eval` 自选评测页（表单式 → promptfoo 引擎）。
- **交互规则 11 条（IR-01~11）**：何时追问、何时出确认卡、确认卡必含字段、`test_count` 覆盖语义、确认前最低校验、进度/报告展示、**脱敏边界**（前端/SSE/进度/报告一律不含原始 prompt/响应/payload/secret/路径）、错误中断、会话隔离、确认后资源准备。
- **历史"消息抖动"根因已在交互层澄清，且架构师确认 P1 修复成立**（SSE 分支与 `pfj-` 分支 `assessment_id` 语义已隔离）；仅剩"SSE 失败回退轮询切换瞬间"需补一条前端单测。

## 4. 目标能力缺口（对照你的三个目标）

| 目标 | 现状 | 缺口 | 等级 |
|---|---|---|---|
| **G1 聊天式自动生成方案** | Skill 链路完整 | 引擎链路无前端对话入口；抖动残留切换瞬间 | 🟡 中 |
| **G2 类 promptfoo 插件/策略扩展** | 有 119 插件/30 策略**静态目录**（L1 对齐）；方案 A 下插件只是**生成标签** | **无原生插件（fail-closed 禁用 `redteam.run`）**；**无专家自定义插件发布**；**三重硬编码无单一来源**；插件不真正驱动生成/判定 | 🔴 高 |
| **G3 Agent 红队** | `kind=agent` 自定义 HTTP（单轮、纯文本） | **无多轮会话**；无有状态/MCP 协议；无副作用隔离；多轮策略未与会话绑定 | 🔴 高 |

> **关键澄清（产品+架构共识）**："像 promptfoo 一样扩展"有两层语义：**(a) 目录/分类对齐（已完成）** 与 **(b) 真正的插件执行逻辑可扩展（未完成）**。维持方案 A 时"新增插件"本质只是给生成 LLM 加分类标签，**其攻击强度取决于生成模型而非插件逻辑**——这直接影响"插件自助注册"的用户预期。
