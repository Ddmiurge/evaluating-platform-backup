## 3. 附：Q-3「聊天里二者选其一」的准确含义

企业聊天工作台确认执行时，MaClaw 的**计划卡（plan_confirm）**会选定"使用能力"，能力分三类来源：

1. **专家数据**（sample / template / composed_attack）→ 走 **Skill 链路**：平台红队 MCP bridge `execute_redteam_evaluation_batch`。
2. **原生 Skill**（CCBOS / AutoDAN / 多模态等已安装 Skill）→ 同样汇入 **Skill 链路**：`manage_skill(run) → register_skill_payload_dataset → execute_redteam_evaluation_batch`。
3. **promptfoo 引擎能力**（plugin / strategy）→ 走 **promptfoo 引擎链路**：BFF `engine_confirm.go` 直接编排 `promptfoo-engine`（方案 A）。

**所以"二者选其一"= 由计划卡里选中的能力类型，决定这次执行走哪条引擎**；一次评测**内部不会两条链路同时跑**（除非未来设计成混合计划）。两条链路都最终落到"调用被测目标 → 判定 → 中文报告"，只是**生成/判定/报告的实现不同**（这正是 `02` F-3、`04` §1 指出的"双引擎张力"）。

## 4. 附：Q-7 两个专有名词解释

### 4.1 "引擎 job 落库"
- **背景**：聊天确认卡只选了 promptfoo 引擎能力时，BFF 走"confirm fast path"（`engine_confirm.go`），会在**平台内存**里建一个 job 记录（`engine_job_store.go`，id 前缀 `pfj-`），用来给前端显示进度。
- **问题**：内存态 = **BFF 进程一重启，这个 job 的进度就没了**，前端可能看到"评测凭空消失"。而另一条 Skill 链路的 job 状态由 MaClawSrv 管理，且 `engine_runs` 表（PG）本来就在记自选评测的 run。
- **"落库"**＝把 fast-path 的这个 job 也**写进 PostgreSQL**（`engine_runs` 或新表），使它与自选评测链路一致、可持久、可恢复、进程重启不丢。
- **代价**：需要新增存储/迁移与状态同步逻辑；收益是可靠性。建议做（DD-6）。

### 4.2 "死表归档后 drop"
- **背景**：数据库现有 26 个 migration、37 张表，**从没删过表**。其中至少 **11 张表在代码里 0 引用**（如 `assessment_logs`/`target_systems`/`assets`/`skill_versions`/`skill_runs`/`external_mcp_servers` 等），是旧架构遗留的"死表"。
- **"归档"**＝drop 之前，先把这些表的数据**导出/备份到冷存**（如 SQL dump 文件、MinIO），留档以防万一。
- **"drop"**＝在归档确认后，写一个**新的 migration**（如 `027_drop_legacy_tables.sql`）执行 `DROP TABLE`，把死表从 schema 移除。
- **为什么要分两步**：直接 drop 不可逆、有数据风险；先归档 → 再 drop，可回滚（从归档恢复）。
- **建议**：做，但**必须另起"数据退役计划"**（`AGENTS.md` 要求），并经你确认后再执行；本阶段只设计不执行。

## 6. 四个决策点的白话详解（DD-2 / DD-5 / DD-7 / DD-8）

> 先给结论：**这四个都是低风险的"工程口径"决策，不影响功能能不能跑，只影响"以后好不好维护、报告好不好看懂"。** 如果你不想逐条纠结，可以直接说"**都按推荐来**"，我可以照此执行。

### DD-2 · 判定双轨与安全分 —— "两条链路判分口径不一样，报告里怎么显示？"

- **它在说什么**：系统里有**两套判断"攻击是否成功"的口径**：
  - **平台口径**（专家数据/原生 Skill 走这条）：分档判定 + 规则快判 + LLM 复核，输出 **0–100 分**，≥80 算攻击成功，**明确拒答一律算失败**。
  - **引擎口径**（promptfoo 走这条）：用一段 `llm-rubric` 让 LLM 判 PASS/FAIL，再翻转成"成功/失败"，**没有 0–100 分**，严重度是靠插件名前缀**猜**的。
- **你在决定什么**：**同一次评测的结果，在报告里用哪套口径、怎么算"安全分/风险等级"。**
  - **A（推荐）双轨分列**：报告按本次实际走的链路显示，并加一句脚注说明两套口径的差别。改动小、不迷惑。
  - **B 引擎独立评分体系**：给引擎单独发明一套评分标准。多一套东西要维护。
  - **C 统一为平台口径**：不管哪条链路，最后都用平台那套**再判一次**，只输出统一的 0–100 分。
- **影响什么**：只影响**报告的分数怎么算、会不会出现"同一目标两条链路分数不同"**。不影响评测本身。
- **推荐 A**（长期可演进到 C）。成本：低。

### DD-5 · 报告 schema 统一度 —— "两种报告要不要两套模板？"

- **它在说什么**：引擎报告和 Skill 报告现在**写进同一张表** `maclaw_redteam_reports`，靠 `metadata.engine=promptfoo` 这个字段区分（"复用同一张表"）。
- **你在决定什么**：前端渲染报告（聊天里的报告卡 + PDF 下载）**要不要维护两套代码**。
  - **A（推荐）复用同一 schema + 加 `engine` 字段**：前端**一套报告组件**同时渲染两种报告。代价小、向后兼容。
  - **B 引擎独立 schema**：前端要写两套渲染/导出/下载逻辑，维护翻倍。
- **影响什么**：只影响**前端工作量和后期维护成本**，不影响报告内容。
- **推荐 A**。基本不用你操心，选 A 即可。

### DD-7 · 目录一致性断言是否阻断合并 —— "改了插件清单忘了同步，要不要拦？"

- **它在说什么**：插件/策略清单现在有**三份**（后端 Go、前端 TS、引擎里的正则词表），目前靠一个"**永远 pass**"的手工脚本同步——也就是说**不同步也不会报错，会悄悄漂移**。
- **你在决定什么**：在 CI 里加一致性检查后，**不一致时是"红灯拦住"还是"只提醒"**。
  - **A（推荐）阻断**：三份不一致 → CI 变红 → 代码合不进去，**强制**先同步。
  - **B 仅告警**：只提示，不拦，靠人自觉。
- **影响什么**：决定**将来"插件显示的数量和实际能用的是否对得上"**——A 是"错不过夜"，B 是"可能悄悄出错"。
- **推荐 A**。**零业务风险**，纯工程护栏，不碰任何功能。

### DD-8 · 死表归档后 drop —— "数据库里 11 张没人用的旧表，删不删？"

- **它在说什么**：数据库 37 张表里，有 **11 张是旧架构遗留、代码里 0 引用**（如 `assessment_logs`/`target_systems`/`assets`/`skill_versions`/`skill_runs`/`external_mcp_servers` 等）。系统**从没删过表**。
- **你在决定什么**：这些**死表**是"**先归档数据、再删表**"，还是"**永远留着**"。
  - **A（推荐）归档后 drop**：先把这些表的数据**导出留档**，确认后再写一个 migration 删掉。
  - **B 长期保留**：不动。代价只是"表越来越多、schema 越来越乱、新人看不懂"。
- **影响什么**：**只影响数据库整洁度和新人理解成本**，不影响任何现有功能。
- **风险**：drop **不可逆**——所以才要"先归档"。**也可以完全不做**（B），代价仅是"表更乱"。
- **推荐 A，但不着急**：放到架构加固阶段（Phase 1）之后，且必须**另起"数据退役计划"、经你确认**才执行。本阶段只设计。

### 附：什么是「引擎 job 落库」（D-11 解释）

- **背景**：当你在聊天里确认的计划**只选中了 promptfoo 插件/策略**时，BFF 走"confirm fast path"直接编排 `promptfoo-engine`，并在**平台内存**里建一条 job 记录（`internal/maclaw/engine_job_store.go`，id 前缀 `pfj-`）——前端用它显示进度。
- **问题**：内存态 = **BFF 进程一重启，这条 job 的进度就没了**（前端可能看到评测"凭空消失"）。而另一条自选评测链路（`/enterprise/eval`）本来就把 run 写进 PostgreSQL 的 `engine_runs` 表。
- **"落库"**＝把 fast-path 的这条内存 job **也写进 PostgreSQL**（复用 `engine_runs`，加 `source=chat_confirm` 区分），使两条链路一致、可持久、**重启 BFF 后进度可恢复**。
- **代价**：需状态写入/恢复逻辑，属中高风险，单独一批（`U5`）。**这是可靠性改进，不是功能变更**；不做也不影响正常评测，只是"重启即丢进度"。
