## 1. 为什么现在可以启动（对 `18` §7 的门槛改口）

### 1.1 事实基础：Plan A 线上零用户

`docker-compose.yml` 的 `PROMPTFOO_ENGINE_NATIVE_GENERATION` 默认 `1`，ai02 实测就是 `1`。Plan A 的"唯一用户"是手动翻转开关的运维，而 `17` 的验收记录写明**回滚验证从未执行**。

**结论：删除 Plan A 对线上行为零改变。** 「保留回滚路径」在证据上是假想的保险。

### 1.2 `18` §7 的两个门槛定位错了

| `18` 的门槛 | 问题 | 重新定位 |
|---|---|---|
| **G-1/G-2/G-3**（P2 全部合入 + 能力矩阵 ≥90%） | 被当作"代码能不能删"的门槛，但 Plan A 的代码只有 **~300 行**（`generateTests.ts` 191 + 测试 101）。矩阵 80% 是**当前生成模型**的表现，不是 Plan C 的天花板 | 代码删除**不需要**通过能力矩阵。矩阵的 80% 属于"换生成模型再测"的运维事项，见 §7 |
| **G-4**（`generation_path` 已标注 ≥2 份报告） | 该字段存在的唯一理由是**两个链路共存期贴标签**；一旦 Plan A 不存在，它退化为历史标记 | 降级为历史渲染需求，不再是启动门槛 |

**真正剩下的门槛只有一条**：删掉 Plan A 之后，产品的**承诺面**是谁——那 9 个维度是承诺的一部分还是不是。本批的答案是：**不是**（按下表逐项处置，且全部显式化，不留静默）。

### 1.3 为什么"两个词汇表并存"本身是缺陷

证据（可复核）：

- 前端策略选择器 **36 项**；其中 promptfoo 认识的原生 id 与平台自造 id **并列摆在同一张表里**（`allPromptfooStrategyEntries` = 平台表 + 动态发现）；
- 平台表里那 9 项在 Plan C 下**没有实现**，转发会抛错、丢弃是**静默**的 —— 向导表单的**默认值**就是其中一项（`strategies: ['direct']`），也就是「什么都不改直接提交」会得到一个 `strategy_stats=none` 的运行且无人告知；
- 原型的策略表（`specs/2026-09-16-前端HTML原型.md`）**本来就已经混着 promptfoo 的 id**（`base64`/`rot13`/`leetspeak`/`best-of-n`/`citation`/`crescendo`/`jailbreak:composite`）与平台自己的（`roleplay`）——说明这张表是按**产品概念**画的，不是按执行引擎画的；
- 在 Plan A 下这 9 项**是真的有效的**：`generateTests.ts:88` 把策略 id 作为**文本**拼进生成提示词（`攻击策略（strategy_id 只能从以下选择）：…`），由平台的生成 LLM 解释并回报。**所以它们的失效不是"当初造错了"，是 U7 换了生成主体之后没人把表换掉。**

## 2. 策略轴收敛（P3-1 / P3-2）

### 2.1 逐项处置（四类，不合并）

| 类 | id | 性质 | 处置 | 替代引导（给用户的话） |
|---|---|---|---|---|
| **A** | `direct` | 不是策略：Plan C 下"不加任何包装"就是直接攻击 | **移除**；后端对命名它的请求显式拒绝；向导默认值改为"不选策略" | 「直接攻击」= 不选择任何策略。Plan C 下默认即直接攻击，不需要额外的策略位 |
| **B** | `encoding`、`otherEncodings`、`multi-turn` | 聚合项：能力**已存在**，只是被包成一个入口 | **下线 + 替代** | 指向已能用的具体原生项：`base64`/`rot13`/`hex`/`leetspeak`/`homoglyph`/`morse`/`piglatin`/`camelcase`/`emoji`；`crescendo`/`goat`/`hydra`/`iterative`/`iterative:tree` |
| **C** | `translate` | 换了表达机制：promptfoo 用 `language` **配置**而非 strategy | **下线 + 记待办**（P3-7，见 §6） | 说明该能力在 promptfoo 里是配置项，平台尚未接入 |
| **D** | `role-play`、`assumed-knowledge`、`few-shot`、`many-shot` | promptfoo **两个槽位都没有**：既不在 35 条原生策略里，也不在 119 个插件里 | **永久移除**（原记的「用 `custom:<variant>` 重新实现」待办 P3-7a 已撤销，见下） | 指向 `jailbreak-templates` / `mischievous-user` / `authoritative-markup-injection` 等原生项，并说明平台自造维度已永久下线 |

> **D 类的依据与「为什么不是待办」**：promptfoo 确实有 `custom` / `custom:<variant>` +
> `config.strategyText` 这个 YAML 原生扩展点（不执行代码；`strategyText` 会被插进发给攻击
> 模型的提示词，实测抓包确认）。也就是说这 4 项**技术上可以在 Plan C 上实现**。
>
> 但「能不能实现」不是这里的判据。这 4 项不是「promptfoo 有、平台没接」，而是**平台自己
> 造的**：实测 `testdata/promptfoo_strategy_catalog.json`（35 条原生策略）与
> `testdata/promptfoo_plugin_legality.json`（119 个插件）确认这 4 个 id 在两个槽位里都不存在。
> 用 `custom:` 把它们实现回来，等于承认平台可以继续自造攻击维度、只是换个更绕的写法 ——
> 而「两套词汇表并存」正是 P3-1 要消除的负债本身（向导的**默认值**曾经就是其中一个，
> 默认提交得到一个 `strategy_stats=none` 的运行且无人告知）。
>
> 所以策略轴的口径定为：**平台的策略词汇表就是 promptfoo 的策略词汇表**。要新的攻击手法，
> 先看 promptfoo 有没有；没有就不提供。`custom` 这个扩展点仍然保留给**专家发布的策略包** ——
> 那是用户内容，不是平台自造维度，两者不能混为一谈。
>
> 记录落在 `retiredStrategyCatalog`（Go）与 `RETIRED_ENGINE_STRATEGIES`（前端）：这 9 条
> **长期保持 9 条**，理由是「永久移除」而不是「待实现」。

### 2.2 机制：复用插件轴已有的那套，不新建

插件轴上一批已经建好「下线 + 理由 + 替代槽位 + 替代 id + 可直接渲染的一句话」：

- `retiredPluginCatalog` + `PromptfooRetiredPlugins` / `PromptfooRetiredPluginGuidance`
- 前端 `RETIRED_ENGINE_PLUGINS` + 可折叠说明
- 后端提交闸 `ValidateEngineRunPluginLegality`（409 `plugin_id_invalid`）
- 护栏：`TestPromptfooRetiredPluginReplacementsResolve`（替代项必须**本环境真能跑**）+ `TestFrontendRetiredPluginGuidanceMirrorsBackend`

**本批为策略轴补齐同构的一套**（`retiredStrategyCatalog` 等），并复用既有测试形状。这是本批的主要新增代码，其余是删除。

### 2.3 三处必须同时改，否则制造新的静默

| 位置 | 改什么 | 不改的后果 |
|---|---|---|
| Go 策略目录 | 9 项移出 `promptfooStrategyCatalog` | 选择器仍提供 |
| BFF 提交闸 | 命名 9 项的请求 → 409 + 理由 + 替代 | 旧配置/直接 API 仍会提交，落到引擎静默丢弃 |
| 向导表单 `initialValues` | 默认策略改为**空**（不选） | 默认值继续是一个已被下线的 id ⇒ 每次默认提交都在静默 no-op |
| 引擎 `nativeStrategyMap` | `PLAN_A_ONLY` 表删除；未知 id 改为**显式拒绝**而不是"丢弃并记 planAOnly" | 引擎仍会静默丢弃（这是 item12 的形态） |

| # | 判据 | 怎么做 | 期望 |

> **判据 5 为什么拆成 5a/5b（2026-10-15 修订）**：原文写的是「默认提交 → 成功且
> `strategy_stats` 不等于 `none`」。但 P3-2 已把向导默认值改成**空**，于是默认提交
> 本来就没选策略 —— 此时 `strategy_stats` 为空是**正确的**，按原文判据一个正确的系统
> 会被判成不合格。真正的反静默判据是 5b：**显式选一个策略，看它有没有被施加**。
> 这与 P3-1 的原始动机一致 —— 当时的病灶是「选了 `direct` 却得到 `none`」，不是「没选却得到空」。

**能力面提醒**：那 4 个无对应项（role-play / assumed-knowledge / few-shot / many-shot）
在 Plan C 上没有实现，所以这次部署后**它们的攻击面不再被覆盖** —— 这是本批的明确取舍
（计划 §2.1 D 类），而且是**永久的**：它们不是 promptfoo 原生策略（35 条策略、119 个插件
两个槽位都没有），用 `custom:` 实现回来等于平台继续自造攻击维度，所以原 P3-7a 待办已撤销。
需要这些手法时应改用 promptfoo 的原生项（例如 `jailbreak-templates`、`mischievous-user`、
`authoritative-markup-injection`），而不是等平台把旧维度加回来。
