== A-1: per-run 落盘是否可行？—— 结论：不可行 ==
落盘位置由两处 module-level 状态决定，都改不动：
  1) getConfigDirectoryPath() = environmentConfigDirectoryPath || ~/.promptfoo
     environmentConfigDirectoryPath 是模块级 let，import 时取一次 PROMPTFOO_CONFIG_DIR
     (logger-*.js:152 `let environmentConfigDirectoryPath = process.env.PROMPTFOO_CONFIG_DIR;`)
  2) getDb() 记忆化连接 (tables-*.js:3819 `if (dbInstance) return dbInstance;`)
     首次调用即把文件固定到进程终结
且无 XDG_CONFIG_HOME / PROMPTFOO_DATA_DIR 等替代env（已 grep 确认）。
=> 并发 worker 下改 process.env 会让 run A 落进 run B 目录；串行化属更大行为变更。
=> 按裁定：不改 PROMPTFOO_CONFIG_DIR，改为显式清理（A-2）。

【这不是读代码得出的，是本批自己踩到的】
第一版端到端脚本用 ESM 静态 import 引入 promptfoo，再给 process.env 赋值 ——
ESM 把 import 提升到赋值之前，于是 PROMPTFOO_CONFIG_DIR 在 promptfoo 捕获之后
才被设置，产物落到了真实的 ~/.promptfoo（residue 读成 false 的假阴性）。
改为「先赋值 + 动态 import」后才拿到可信读数。误操作已清理（-wal/-shm 已删）。

== A-2: 清理钩子三路径端到端（真跑 promptfoo 原生生成）==
落地: src/runner/promptfooStateCleanup.ts + TaskManager.onTerminal
      （挂在 runSafe 的 finally —— 三条终态路径唯一汇合处）
清理目标: promptfoo.db / -wal / -shm / evalLastWritten / cache/
刻意不删: auth.json、用户自写的 promptfoo.yaml（不是我们建的）

路径            phase / error_code                     清理前有残留  清理后  剩余产物
成功            failed / engine_error(strict 拦 0 用例)   true        false   []
失败            failed / forced_failure                 true        false   []
中止            canceled / canceled by user            true        false   []
（「清理前有残留=true」是关键：证明 promptfoo 真的写了，清理不是空转）

清理失败 -> PromptfooStateCleanupError（只含路径与 errno，绝不含 payload）
  * 仍 succeeded 的 run -> 降级 failed + terminal_cleanup_failed（不静默留残留）
  * 已 failed/canceled  -> 保留原错误码（别用清理问题覆盖真实原因）
反证：hook 去掉 -> expected 'succeeded' to be 'canceled'；已还原

== 顺带修掉的真 bug ==
runSafe 原先只在 execute() 抛错时才把中止的 run 标 canceled；若 execute() 在
abort 后正常返回（runner 吞掉 abort / 恰好同时完成），会被标 succeeded ——
被取消的运行显示为绿色成功。已加 signal.aborted 前置判断 + 反证。
