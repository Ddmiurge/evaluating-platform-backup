## 0. 一页结论

| 问题 | 答案 |
|---|---|
| 这是什么 | 第三级放开：给「必须编译进引擎本体」的插件开的**评审制**交付通道 |

| 谁放行 | 三道门：**自动关卡**（静态扫描+包内测试）→ **管理员人工审核**（可看源码）→ **构建验收**（实测表重生成+全守卫+验收记录） |

## 1. 目标与非目标

### 1.1 目标

1. 专家**自助交付**内嵌插件（不再要求 git 贡献流程），与 YAML 插件/策略包/Skill 的门户体验一致；
2. 三道门全部自动化可执行，**驳回必须可操作**（知道改什么、怎么改）；
3. 修改循环是一等公民：重传、版本、历史、逐关重跑都有明确语义；
4. 构建后**全员可用**（主理人硬要求，2026-11-04/09 两轮确认）；
5. 治理时效与数据包拉平：停用即时、移除随构建；
6. 共享引擎的全部既有验收（51 轮）不失效——新镜像有自己的出生证明。

### 1.2 非目标

| 不做 | 理由 |
|---|---|
| 改写成 YAML 外挂 | 主理人已否（2026-11-05）：内容装不下（判分钩子/多阶段编排/确定性证据计算不在 YAML 契约里） |
| 每租户专属镜像舰队 | 当前单信任域下隔离是空收益，却引入每租户开通时差；留作信任模型变化后的演进（复用本稿①→③） |
| 上传即生效 / 热加载进运行中引擎 | 编译产物没有运行时门；生效必须经过构建 |
| 未审核包对企业可见 | 半成品选了必失败；企业目录只收「已入镜像」的 id |
| 自动构建（无显式触发） | 构建=部署事件，必须有人按下扳机；审批可以攒，构建显式触发 |

## 2. 背景：三级放开模型（为什么内嵌要评审制）

平台按**危害上限**决定治理强度（2026-11-09 对话定型）：

| 级 | 载体 | 危害上限 | 治理 | 自助度 | 现状 |
|---|---|---|---|---|---|
| 1 数据 | YAML 插件 / 文本策略 | 污染结果（可归因可停用） | 事后治理 | 完全自助 | ✅ 已放开 |
| 2 盒中代码 | JS 策略（纯函数盒：禁网/超时/输出校验） | 被盒子圈住 | 运行时闸（开关+专属实例） | 自助发布 | ✅ 已放开 |
| 3 本体代码 | **内嵌插件**（读响应、挂钩子、可编排） | **进程沦陷（能偷）** | **事前人审+构建验收** | 上传自助、放行评审 | ← 本稿 |

关键事实：内嵌插件**没有运行时门**（promptfoo 的编译期 API 无运行时加载口），只能进镜像——所以它的闸必须建在「进镜像之前」，这正是三道门的由来。

## 3. 包格式与上传契约

### 3.1 形态

| 项 | 取值 |
|---|---|
| 载体 | **单个 zip**（专家门户文件选择，≤ 512 KB 解压后；zip 内文件数 ≤ 64） |
| 结构 | `manifest.yaml` + `src/`（插件源码）+ `tests/`（包内自测，必须可跑） |
| 存储 | 复用 `maclaw_resources` 加密存储，**新 kind：`pf_plugin_embedded`** |

**为什么新 kind 而不是 `pf_plugin` + 形态位**：`pf_plugin` 的语义是「运行时 YAML 包」，会流入企业目录（`pf_plugin:<handle>` 引用、shadow 投影、P23 专家互览合并）。内嵌包在烘焙前**对任何人都不该可选**——新 kind 天然不进这些通道，一行白名单都不用加；烘焙后它以**内置 id** 身份进目录，与资源目录彻底分家。

### 3.2 manifest.yaml（发布期逐项校验）

```yaml
id: semantic-cache-collision      # 全局唯一；禁止与内置 116、已批准/已入镜像 id 冲突
name: 语义缓存碰撞检测
category: injection               # 只允许现有 11 个类别值（前端镜像不爆炸）
severity: high                    # critical|high|medium|low
promptfoo_base: "0.123.0"         # 必须等于当前冻结基座，防"对着别的版本写的包"
entry: src/plugin.ts
tests: tests/                     # 零依赖、离线可跑（见 §3.3）
summary: 检测跨用户语义缓存复用…
```

### 3.3 上传期拒绝（存储出口，沿用 P10/P19 纪律）

- zip 安全：路径穿越（`../`、绝对路径）、符号链接、解压炸弹（单文件/总大小/文件数上限）；
- 静态令牌扫描：`process.env` / `fs` / `child_process` / `fetch` / `eval` / `new Function` / 远程动态 import —— **和代码策略同一张拒绝表**（内嵌插件进的是密钥进程，门槛只高不低）；
- manifest 缺字段 / id 冲突 / base 版本不匹配 → 拒绝并给可操作原因（沿用 rejection hints 模式）；
- **包内测试约束（2026-11-10 主理人确认）**：必须**零依赖、离线可跑**——纯 `node` 脚本可执行（如 `node tests/run.mjs`），禁止 `npm install`、禁止网络；上传期在引擎子进程限时（≤30s）实跑，跑不过即拒。理由：摩擦循环的反馈速度——改完重传秒级知道行不行，而不是等构建批次；要拉依赖的包在上传期就把依赖问题暴露，而不是烤进镜像才发现。子进程只拿**最小环境**（`NODE_ENV` 与 PATH/TMPDIR/LANG/TZ 等无密钥变量），不再继承引擎进程的 `process.env`——静态扫描禁用 `process.env` 字面量只是抬高门槛，不是边界（2026-11-12 加固）。

### 3.4 插件 entry 契约（引擎加载口径，2026-11-11）

`manifest.entry` 指向的文件由引擎在**被选中跑评测时**动态 import（懒加载：坏包只炸它自己那一跑，不拖垮共享引擎），因此它必须满足：

```ts
// src/plugin.ts
export default {
  // promptfoo 原生 action 签名；返回值是 TestCase[]
  async action(params: { provider; purpose; injectVar; n; config; /* … */ }) {
    return [
      {
        vars: { [params.injectVar]: '攻击载荷原文' },   // 必填：非空字符串
        assert: [{ type: 'llm-rubric', value: '判定标准…' }], // 必填：非空数组
      },
    ];
  },
};
```

- **每条用例必须带非空 `assert`**：没有断言时 promptfoo 恒判 `pass=true`，而红队归约把 `pass=false` 当作「攻击成功」——静默假阴性（每条都显示攻击失败）比报错更糟。loader 在运行时逐条校验并抛错。
- **`vars[params.injectVar]` 必须是非空字符串**：注入变量由运行配置决定，loader 按当次 `injectVar` 校验。
- **TypeScript 只允许可擦除语法**（Node 24 原生 type stripping）：不能有 `enum`、`namespace`、参数属性等；相对 import 必须带显式扩展名（`./util.ts`）。
- 包内测试 `tests/run.mjs` 应断言 action 的输出形状（上传期只校验导出形状与包内测试，不调用 action——调用需要 stub provider，误判风险大于收益）。
- 上传期 probe（引擎 `POST /embedded-packages/validate`）在包内测试通过后**额外 import entry 并检查 `default.action` 是函数**，不满足即拒（`embedded_entry_contract`）。

## 4. 状态机与修改循环（摩擦处理的一等公民）

```
   专家上传 ──► 待初审 ──自动关卡不过──► 已驳回 ──专家改包、同 id 重传──┐
                  ▲                      ▲                           │
                  │  └──初审「需修改」+意见（必填）──┘                   │
                  │                                                    │
                  ├──初审通过（管理员，看代码）──► 已批准·待构建               │
                  │        │ 管理员点「请求构建」→ 已请求构建（标记留痕）      │
                  │        ▼  部署机工具消费标记（拉库→解密→烤镜像→         │
                  │           实测表重生成→全量守卫；无标记则拒绝执行）        │
                  │        │  守卫不绿：批次回「构建失败+摘要」，不落地     │
                  │        ▼                                         │
                  │  测试中（已烤进镜像、已在线，但只对                  │
                  │         测试白名单账号可见可选）                      │
                  │   ├─测试中改包→同 id 重传→全关卡→待初审→…再构建 ──────┘
                  │   └─测试账号真跑的 run = 验收证据
                  │        │
                  │        ▼  管理员看过测试 run 后手动「最终通过」
                  │  已通过·全员可选（进共享目录，亮灯，与内置无差别）
                  │        │
                  │        ├─ 停用 → 提交闸即时 409（不等重建）
                  │        └─ 移除 → 下次构建剔除 → 目录消失
```

**状态机的六条硬规则**：

1. **重传 = 同 id 更新**：沿用 P10 语义（请求带已有 `id`，handle 复用）——绝不因改一版而出现第二个包（P10 的「递增版本变两个包」教训不重演）；版本号递增，历史版本可追溯（谁在哪版被谁审的）；
2. **驳回原因必须可操作**：自动关卡给「哪条规则、哪个文件」；管理员「需修改」**意见为必填**，指向具体问题（沿用 rejection hints 的「可执行下一步」标准）；
3. **每轮重传重跑全部关卡**：自动关卡不因「上次过过」而豁免；初审重新从头（换人审也成立）；
4. **并发防撞**：id 在上传时初查、**批准时再查**（防两个专家同时传同名包，先批者得，后批者收到冲突驳回）；
5. **两段审批不可合并**（2026-11-10 主理人定）：初审=「可以构建去测」，最终通过=「可以放行给所有人」；**「测试中」不进全员目录、不自动跳变**——最终通过必须是管理员看过测试 run 后的手动动作；
6. **测试中可见性=白名单**（主理人选 a）：该 id 仅对管理员指定的测试账号可见可选；普通企业用户全程**看不到**半成品（不复活被否掉的灰按钮问题）——白名单是临时生命周期阶段，不是永久能力分层。

## 6. 关键设计决策

| # | 决策 | 理由 |
|---|---|---|
| D-1 | 上传面=专家门户、审核面=管理员门户、构建面=仓库 CI 流水线 | 主理人定型（2026-11-09）；专家不是 git 协作者，三面各归其位 |
| D-2 | 三道门缺一不可，且**顺序不可换** | 静态关卡拦机器可判的（省人审时间）；人审拦机器判不了的（恶意逻辑）；构建验收拦集成问题（和别人打架、表没重生成） |
| D-3 | 未烘焙的 id **根本不进企业目录** | 没有灰条阶段——「选了必失败」的选项不该存在；企业永远只见成品（比灰条方案更简单，2026-11-09 随舰队方案一起废弃） |
| D-4 | 生效=烘焙进共享镜像+实测表重生成 | 这是「全员可用」的唯一自然达成方式；`gen_plugin_legality` 在扩展镜像上重跑后，新 id 变合法、进主目录，亮灯 |
| D-5 | 停用走**提交闸**（即时），移除走构建（异步） | 镜像里的东西删不掉，但「允许选」是运行时可拦的——复用 retired/远程闸同一张提交闸，治理时效与数据包拉平 |
| D-6 | 审批可攒、构建显式触发、**守卫不绿不部署** | 构建=部署事件；批次原子性：任一守卫红，整批不落地（宁可推迟生效，不可带病亮灯） |
| D-7 | 构建机制 = **一次性基建补丁 + 每插件纯文件投放**（Step-0 已落定，见 §11） | `redteam.run` 两条配置入口都 `yaml.dump` 成文件、`plugins` 为字符串数组——插件对象结构上无法存活，对象注入路线死刑；补丁通用化后**新增插件零补丁工作**，只有 promptfoo 升级时重合一次基建补丁 |
| D-8 | 新 kind `pf_plugin_embedded` | 见 §3.1：天然隔离于运行时包的全部分发/互览/引用通道 |

## 10. 验收判据

1. **上传**：zip-slip / 超限 / 带 `process.env` 的包 → 上传期拒绝且原因可操作；合法包 → 待审核、加密落库、企业与其他专家均不可见（新 kind 不进任何分发通道）；
2. **修改循环**：驳回 → 改 → 同 id 重传 → 版本+1、无重复包、全关卡重跑；管理员「需修改」不带意见无法提交；
3. **初审**：通过→待构建；并发同 id 二查生效（后批者冲突驳回）；
4. **构建触发与执行**：点「请求构建」→ 状态=已请求构建且标记落库（谁/何时）；工具无标记执行被拒；工具消费标记执行——实测表重生成使新 id 合法、全守卫绿才部署；任一守卫红 → 批次不落地、状态回待构建+失败摘要；
5. **生效**：所有企业租户向导里新 id 亮灯可选（与内置无差别），真跑出报告；
6. **测试中**：仅白名单账号的向导里可见可选该 id，普通企业账号**完全不可见**（搜不到、下拉无此项）；测试中改包重传 → 版本+1、仍处测试中、全关卡重跑；
7. **最终通过**：管理员手动操作前该 id 绝不进入全员目录（无自动跳变）；操作后全员可见可选、真跑出报告；
8. **治理**：停用 → 下一次提交 409（不等重建）→ 恢复可用；移除 → 下次构建后目录消失；
9. **回归**：51 轮既有判据在新镜像上重跑关键子集绿；数据包/策略包全链不受影响（P10/P19/P26 判据各抽验一条）。

## 11. Step-0 实测结果：构建机制落定（2026-11-10）

源码级实测（promptfoo `0.123.0`，tag `3ec9740`），无需运行探针——两条配置入口的终点都是 YAML：

| # | 待测 | 结果 |
|---|---|---|
| 1 | `redteam.run`（`doRedteamRun`）能否接受插件**对象** | ❌ 不能。入口只有两个：`options.config`（YAML 文件路径）与 `options.liveRedteamConfig`（内存对象，但**立即 `yaml.dump` 到临时文件**再当路径用）——函数/类实例无法被 YAML 序列化 |
| 2 | 配置里 `plugins` 的类型 | `z.array(z.string())`（`types.ts:172`）——只有字符串 id / `file://` 数据文件引用能过 schema |
| 3 | `file://` 能否指向 TS 代码插件 | ❌ 那是 CustomPlugin **数据文件门**（generator+grader YAML，U10 验证过的路径）；编译期插件 API（`plugins.ts`/`graders.ts` 注册表）无运行时加载口——与插件包 README 自述一致 |

**结论：Route A（零补丁对象注入）死刑，走 Route B——但做成通用形态**：

- **一次性基建补丁**（进我们仓库的构建过程，不是对每个包打）：给 promptfoo 的插件注册表加一个"从 `embedded-plugins/index` 追加加载"的口子；
- **每个插件 = 纯文件投放**：包文件进暂存区 + index 由构建脚本从 manifest 生成——**新增插件零补丁工作**；
- **重合成本收敛为每次 promptfoo 升级一次**（重合这一个基建补丁），不是每个包 12 处；
- 该补丁与生成器链一起在升级时重验（既有纪律）。

本节取代 D-7 的"待实测"，E-4 的实现以此为准。

### 11.1 Route B 实施（2026-11-11）

两道门实测位置（promptfoo 0.123.0 dist）：

1. **schema 门**：`dist/src/tables-*.js`（index.js 实际 import 的那块，hash 名）的 `pluginOptions`（`COLLECTIONS ∪ ALL_PLUGINS ∪ ALIASED_PLUGINS`）是 `RedteamConfigSchema` 的枚举来源——未知 id 且非 `file://` 前缀 → `safeParse` 抛 `Invalid redteam configuration`；
2. **注册表门**：`dist/src/index.js` 的 `const Plugins = [...]` 按 `key` 查找，缺席即 `logger.warn("not registered, skipping")` → 0 用例 → `strict:true` 抛 `PartialGenerationError`。

补丁脚本 `promptfoo_engine/scripts/patch-embedded-plugins.mjs`（`npm run patch:embedded`；Dockerfile build stage 执行）向**已安装的 dist** 注入两段带 marker 的代码：

- tables：追加 `...__p28EmbeddedPluginIds` 到 `pluginOptions`（id 列表运行时读 `PROMPTFOO_EMBEDDED_PLUGINS_DIR/index.json`，构建期不烤数据——重新 stage 无需重打补丁）；
- index.js：包级追加 loader 条目 `{key, action}`，action 懒加载 entry、逐条校验 3.4 的契约。`index.json` 缺失（全新 clone 未 stage）→ 静默空表；**格式损坏 → import 期抛错**（引擎启动即崩、healthcheck 红 = D-6「不绿不部署」）；单个包坏 entry → 仅被选中时抛错。

纪律：锚点缺失 → 脚本 exit 1（promptfoo 升级后必须重测锚点，绝不静默发出未打补丁的镜像）；marker 幂等（重复执行不叠加）；`vitest` 的 `patchEmbeddedPlugins.test.ts` 对着**真实安装的 dist** 校验锚点（升级绊线）并把注入块原样抽出来在临时目录跑行为断言。

内嵌插件的报告分类/severity/judge 档走 **Go 侧 `PromptfooEngineCatalog()`** 单点追加（见 `maclaw-current-state.md` 的 P28 节）：BFF 推送的 catalog 是引擎归约器读取 severity/category/judge_source 的唯一通道。

部署机编排壳 `evaluating_platform/scripts/embedded-build.sh`：`-stage`（NO_QUEUE 即退出，跳过部署与定格）→ 构建 **engine + backend 两个镜像**（引擎 COPY 暂存树，backend 编译期 embed 向导目录——只重建一边就是「目录里有 id、引擎跑不了」的双视图）→ 重建容器 → 等 Docker healthcheck 绿（不绿不部署）→ `-finalize -ok`；中途任何失败走 `-finalize -fail -reason=…`（安全摘要，进审计事件与门户），定格失败单独 exit 4 且保留 index 供重试。`--root` 是**平台目录**（`internal/` 与 `promptfoo_engine/` 的父目录），默认取脚本父目录；`cmd/embeddedbuild` 在连库前校验该形状，错根不再留下仓库根的多余暂存树（54 号 §6.3）。**部署机需要 Go（≥1.22）**：批次工具要在宿主上读写平台目录并连库，脚本因此先做 `go` 预检并以 exit 64 明确失败；没有 Go 的宿主机目前不能直接跑完整脚本（55 号 §8）。

契约违例的可诊断性（54 号 §6.4）：promptfoo 把 action 异常吞在 `Promise.allSettled` 里，只留一行 warn + 聚合的「0/2 tests」。loader 的错误信息带 `case #N`，引擎记录器 `createDiagnosticLogCollector().embeddedPluginError()` 从原始行里提取后映射为 `native_generation_embedded_plugin_invalid`（原因进 `error_brief`；前端有对应中文解释）——与「模型拒答」同一类：可操作原因单独成码，重试不会改变结果。
