## 3. 本轮发现的缺陷

### 3.1 P2：目标调用没有超时；无回答的探针会让 run 永久挂起，且 cancel 不释放工作线程

实测时间线（`er-05e324298b15427dbc400ce46de70b43`，contracts + base64，6 探针）：

| 时刻（BJ） | 事件 |
|---|---|
| 14:47:35 | run 启动 |
| 14:47:36 | 引擎日志 `Running 6 test cases (up to 4 at a time)...` |
| 14:47:37 | 6 条请求全部发到靶机；3 条有回答、3 条 `answer` 永久为空 |
| 14:47:56 | `executed_count=1` |
| 15:02 | `executed_count=2`，此后不再变化 |
| 15:04 | 人工 cancel → 记录变 `canceled`，但**引擎进程仍占着唯一 worker**（日志停在 `Running 6 test cases`，无终态输出） |
| 15:06 | 新提交的 run `er-daeae716abfa451ea7dd23cd51e9c2d8` 一直 `queued`，永远不执行 |

两点需要修复：

1. **每次目标调用必须有超时**（promptfoo http provider 的 `config.timeout` 当前未下发；`redteam-config.yaml` 里 provider 只有 `url`，无任何超时字段）。超时后应走既有分类链路记为 `未取得回答（调用失败：超时）` 并继续下一个探针，而不是无限等待。
2. **取消必须能终止正在执行的探针**（AbortController / 关闭连接），否则 cancel 只是把数据库状态改成 `canceled`，worker 被僵尸占住，`ENGINE_WORKER_COUNT=1` 的串行设计会把整个引擎锁死——实测后续 run 永远 `queued`，只有 `--force-recreate` 引擎才能恢复。

### 3.2 OPS：`docker restart ep_promptfoo_engine` 会进入重启循环

```
[engine] fatal: ConnectionFailed("Unable to open connection to local database /home/node/.promptfoo/promptfoo.db: 14")
```

- 触发：对引擎容器执行 `docker restart`（不是 `up --force-recreate`）。
- 原因：`/home/node/.promptfoo` 是 `tmpfs`（`read_only: true` 下唯一的可写面），restart 后 libsql 打开该路径返回 `SQLITE_CANTOPEN`，进程 fatal exit，容器重启循环，健康检查一直 `unhealthy`。
- 恢复：`docker compose up -d --force-recreate promptfoo-engine` → 3 次健康检查内恢复 healthy（实测 `healthy @ 第 4 次探测`）。
- 建议：运维手册把「引擎重启」写成 `--force-recreate`；或在启动脚本里对 `.promptfoo` 目录做一次可写探测 + 自适应处理后重试一次。

## 5. 结论

1. `96163f8` 代码本身在平台侧判据上**全部通过**，无回归：策略不翻倍、无策略基线、报告卡三核、移除只做减法、追加只收策略、脱敏标注、报告口径与禁用值边界都对；
2. 本轮真正的阻塞在**靶机侧**：Dify 靶场应用的上游模型今日 429 限流 + 404「没有此模型」，半批探针拿不到回答；
3. 由此撞出**平台 P2 缺陷**：目标调用无超时 + cancel 不释放 worker，会让整个引擎锁死（§3.1），建议优先修；
4. 另需在运维手册固化**引擎用 `--force-recreate` 重启**（§3.2）。
