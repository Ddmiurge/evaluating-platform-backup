## 8. 本轮环境故障与绕过（与 P22 无关，但决定了这一轮怎么跑完）

### 8.1 容器内 DNS 全断（比 10-27 那次更严重）

P22 复验 B 第一次跑（`er-07f3f03b5575485baf2c0ec7004844f4`）失败，`error_code=native_generation_promptfoo_failed`、0 探针。引擎日志给出的真因不是策略代码，而是**引擎容器解析不到生成模型端点**：

```
API call error: Error: Request failed after 4 retries: TypeError: fetch failed
  (Cause: Error: getaddrinfo EAI_AGAIN api.xiaomimimo.com)
Failed to generate tests for contracts / Generated 0 tests for contracts
```

对照证据：

| 侧 | `api.xiaomimimo.com` 解析 | 备注 |
|---|---|---|
| 引擎容器 | `EAI_AGAIN`（v4/v6 都失败，`wget: bad address`） | `/etc/resolv.conf` → `nameserver 127.0.0.11`，`ExtServers: [223.5.5.5 114.114.114.114]` |
| 宿主 | `202.69.4.23` 正常 | 真实解析器是 `10.95.38.38`（`resolvectl status`） |

即 Docker 守护进程给容器配的外部 DNS（`daemon.json` 里的 `223.5.5.5` / `114.114.114.114`）在本网络不可达，而宿主真实解析器是内网 `10.95.38.38`。同一个病根也解释了本轮**镜像构建卡在 `npm install`（`EAI_AGAIN registry.npmmirror.com`）99 分钟**。

**绕过**（不改仓库内任何 compose 文件）：加了一个临时 override 文件 `/var/tmp/p22/docker-compose.dns.yml`，只给 `promptfoo-engine` 指定 `dns: [10.95.38.38]`，用 `-f docker-compose.yml -f /var/tmp/p22/docker-compose.dns.yml up -d --force-recreate promptfoo-engine` 起容器。之后容器解析正常（`220.181.104.192 mimo-pri-prod.alb.xiaomi.com api.xiaomimimo.com`）。

**⚠️ 遗留风险**：容器当前的有效配置依赖那个临时 override；下一次有人用**不带 `-f`** 的 `docker compose up -d` 重建引擎，DNS 会退回坏配置、生成链路再次全断。长期修法二选一（都需要用户拍板）：

1. 仓库内 `docker-compose.yml` 给 `promptfoo-engine`（以及 backend）加 `dns: 10.95.38.38`——会改代码，属修复批次，本轮没动；
2. 宿主 `/etc/docker/daemon.json` 的 `dns` 改为 `10.95.38.38`——影响全机所有容器（还有 dify / higress / openclaw 别的栈），要重启 dockerd，必须用户同意。

### 8.2 离线构建（DNS 全断时唯一出路）

- 引擎：源码树里已有 `node_modules`，直接 `node node_modules/typescript/bin/tsc -p tsconfig.json` 编出 `dist`，再以旧引擎镜像为基 `COPY --chown=node:node dist /app/dist`；
- 后端：`golang:1.25` 容器内 `GOPROXY=off go build`（命名卷 `ep_gomodcache` / `ep_gocache` 复用缓存），再以旧后端镜像为基 `COPY server /app/server`。

两处都用 `--force-recreate` 部署，engine/backend healthy、`/health` 200。

### 8.3 一个顺带确认的可诊断性缺口（不改代码，只记录）

`engine_runs.error_brief` 里**有**精确诊断（D/E 两条都能读到“哪个包、什么原因”），但 `GET /api/v1/maclaw/engine/runs/:id` 的 DTO **根本不回显 `error_brief`**（返回体字段：`id/phase/status.../error_code/current_stage/...`，无错误文本），前端 `src/` 里也搜不到 `error_brief`。也就是说**用户和企业门户只能看到错误码，看不到原因**，原因要去库里查。

建议（后续修复批次，非本轮）：把 `error_brief` 加入 run DTO 并按 `error_code` 决定是否展示，或至少提供“失败原因”一行。注意 redaction 已在两条通道各做一次（`engine_error_brief.go` / `errorBrief.ts`），加 DTO 字段不需要放宽任何脱敏规则。

## 10. 遗留

1. **容器 DNS**：见 8.1，需要用户在“compose 加 `dns:`”和“改 `daemon.json` 重起 dockerd”之间选一个，否则下一次不带 `-f` 的 compose 重建会把生成链路打回全断。
2. **`error_brief` 不进 API DTO**：见 8.3。
3. **同步死循环仍不可兜底**：`while(true)` 型恶意/缺陷代码会占死单 worker（设计文档 §15.3b 已声明）。共享部署保持开关关闭是当前唯一缓解。
4. 复验产生的临时资源（三个代码包：`p22off` 409 拒绝未落库、`platform_resource_9a933ea7…`、`platform_resource_71841ea8…`）留在专家目录里，可按需下架。
