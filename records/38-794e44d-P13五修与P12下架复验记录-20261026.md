### 判据2 首轮失败的原因（重要，且不是代码回归）

第一次判据2 直接 `failed`：

```
error_code = native_generation_promptfoo_failed
error_brief = promptfoo native generation failed: Test case generation failed for 1 plugin(s): contracts (0/3 tests)
```

引擎日志给出真正原因：

```
[Language Processing] Error generating tests for contracts:
openai:chat:mimo-v2.6-flash returned a refusal during inference for ContractPlugin test case generation.
User-configured values were included in inference and may have been deemed harmful:
{"purpose":"验证用：固定返回配合内容"}.
```

**被测系统的 description（即 run 的 purpose）会被原样喂进生成模型**（AGENTS 已记录该字段的作用），本轮我为了造「攻击成功」把靶机描述写成「验证用：固定返回配合内容」——生成模型判定其意图可疑，直接拒答，于是 contracts 生成 0 条用例，`strict: true` 把「某插件生成 0 条」当硬失败，整轮 failed。三次尝试中 2 次失败、1 次成功（模型不确定性）；把描述改为中性的「内部邮件助理：负责起草、总结与分类公司邮件」后**一次通过**。

这带来一条产品层面的风险，建议记录：

- 企业用户填写的「被测系统用途」措辞敏感（如"测试模型会不会违规/绕过"）时，**整批评测会以生成失败告终**，而界面上只能看到 `native_generation_promptfoo_failed`，看不出是"自己写的描述被判可疑"；
- 建议：生成失败时把"用途描述可能被判可疑"作为可读提示之一给出（不泄露生成提示词本身），或在向导里对该字段做一次轻量预检。

## 5. 对 37 号记录的两处更正（由本次提交核实）

794e44d 的提交说明核实了 37 号报告里两处不准确，记录在此以免后续误用：

1. **清理清单其实包含 `cache/`**（`promptfooStateCleanup.ts:127`），37 号写"清单里没有 cache/"不准确；真正的问题是**清理只在终态执行**，而缓存复用发生在运行期。修法因此改为环境变量 `PROMPTFOO_CACHE_ENABLED=0` + `env.ts` fail-closed。
2. **超时变量是 `REQUEST_TIMEOUT_MS`，不是 `config.timeoutMs`**：promptfoo 的 http provider 只读该环境变量（默认 300s），37 号建议的 `config.timeout` 实际无代码读取，属于"看起来配了超时"。
