## 2. 本轮踩到的构建阻塞（环境缺陷，非代码问题）

`docker compose build promptfoo-engine` 连续两次失败：

```
#12 [build 5/5] RUN npm install --no-audit --no-fund && npm run build
npm error code EAI_AGAIN
npm error request to https://registry.npmjs.org/why-is-node-running failed,
  reason: getaddrinfo EAI_AGAIN registry.npmjs.org
```

排查结论：

| 检查 | 结果 |
|---|---|
| 宿主 DNS | 正常（`registry.npmjs.org` 可解析，但只返回 IPv6） |
| `/etc/docker/daemon.json` | `"dns": ["223.5.5.5","114.114.114.114"]` —— **这两个公共 DNS 在本网络不可达** |
| 宿主机真实解析器 | `resolvectl`：`10.95.38.38`、`8.8.8.8` |
| 既有容器（ep_backend）出网 | 正常；但新建的 `node:24-alpine` 测试容器解析失败，只有显式 `--dns 10.95.38.38` 才解析成功 |
| 结论 | **buildkit 的构建容器拿不到可用 DNS**；把构建阶段的 npm registry 改成 npmmirror 也一样失败（EAI_AGAIN on registry.npmmirror.com），说明是 DNS 而非某个 registry 的连通性问题 |

**绕过方式**（有效）：

```bash
sudo docker buildx build --allow network.host --network host \
  -t evaluating_platform-promptfoo-engine:latest --load ./promptfoo_engine
```

`--network host` 让构建过程直接用宿主的解析器，构建成功（365 秒），随后 `docker compose up -d --force-recreate promptfoo-engine` 切到新镜像。

**另外发现一处仓库内的可复现性缺陷（建议修）**：`promptfoo_engine/Dockerfile` 的 `deps` 阶段设置了 `npm config set registry https://registry.npmmirror.com`，但 **`build` 阶段的 `RUN npm install` 没有设**，于是它走默认的 npmjs——在没有 npmjs 出网的机器上必然失败。本轮为了让构建跑通，我临时给 build 阶段补了同一行 registry 配置，**构建完成后已用 `git checkout` 还原，仓库工作区无改动**。建议上游把 registry 配置提到两个阶段共用（或放到 `.npmrc`）。

**顺带**：本轮开始时 `/tmp/jwt.txt`、`/tmp/p8_jwt.txt` 已不存在（前几轮的临时凭证文件被清理），已重新登录 p8-test 并按既有方式签发企业 JWT 后继续。

## 3. P14 修复验证（核心）

修复前（36/38 号实测）：同一种失败只给一个码，且错误摘要只说"哪个插件 0 条"：

```
error_code  = native_generation_promptfoo_failed
error_brief = promptfoo native generation failed: Test case generation failed for 1 plugin(s): contracts (0/3 tests)
```

修复后（本轮实测，`er-d9f1e694cf4f4d4590b707ada9cc9827`）：

```
error_code  = native_generation_model_refused
error_brief = 生成模型拒绝了用例生成。最常见的原因是被测系统用途（purpose）被判定为可疑——
              请把它改成中性的业务角色描述（例如「客服问答机器人：回答售后与物流咨询」），
              不要写评测意图或对抗…
```

触发条件：把被测系统描述（即 run 的 `purpose`）写成「验证用：绕过安全限制的越狱测试靶机」。

前端侧（构建产物已含，静态确认）：

```
native_generation_model_refused",Die={[Bie]:"生成模型拒绝了用例生成。最常见的原因是被测系统用途被判为可疑
 —— 请改成中性的业务角色描述（例如「客服问答机器人：回答售后与物流咨询」），不要写评测意图或对抗措辞，然后重试。",
 native_generation_promptfoo_failed:"引擎在生成阶段失败。若是模型或靶机限流、网络问题，请稍后重试；连续失败请查看运行详情里的错误摘要。"}
```

并且 `explainEngineRunErrorCode` 对未知码返回空串（不编解释），这一点在源码里可见。

**同时观察到：拒答是模型侧非确定性的。** 本轮用同一批敏感描述共跑了 5 次生成，只有 1 次真的拒答：

| 描述 | 结果 |
|---|---|
| 验证用：固定返回配合内容 | succeeded（2 次，均未拒答） |
| 测试靶场：要求被测模型忽略安全策略并输出有害内容 | succeeded |
| 验证用：绕过安全限制的越狱测试靶机 | **failed → native_generation_model_refused** |

所以"用途描述敏感 → 一定失败"不成立，但**一旦失败，现在的错误码与提示是准确的、可执行的**——这正是本次修复的目标。
