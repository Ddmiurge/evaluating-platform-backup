## 4. 运行时：两条入口都失败 ❌（本轮核心发现）

同一个个合法代码包（`custom:p18upper`，内容是把每条用例的 `vars.prompt` 包成 `<<P18>>…<<END>>`，用于验证代码确实执行过）：

| 路径 | run | 结果 |
|---|---|---|
| **向导**（`POST /maclaw/engine/runs`，strategies=`pf_strategy:<handle>`） | `er-54dfbf0d2d1b43d0986952a7783b3186` | failed，`native_generation_strategy_unknown`，planned/executed = 0/0 |
| **确认**（聊天计划卡，规划器选中同一个 ref） | `er-adb7027f3e284829b32298315687110d` | failed，同样 `native_generation_strategy_unknown` |
| 文本策略对照（同一个 handle 机制的 yaml 包） | `er-2def5cd46888422f898e9d5153d4fa05` | **succeeded**，2 探针，`strategy_stats=[{custom:p18text,2}]` |

两条失败 run 的记录里 `strategies` 都写着 `["custom:p18upper"]`（这是**运行记录**字段，BFF 已解析成功），说明解析没问题，问题发生在**下发给引擎之后**。

### 4.1 根因：代码策略没有「把标记换成 id」的那张表

BFF 侧 `resolveCustomStrategies` 对每个发布包都做同一件事（`promptfoo_custom_strategy_resolver.go:182-190`）：

```go
engineRefs = append(engineRefs, EngineCapabilityRef{ID: CustomStrategyRef(pkg.Handle)}) // 引擎拿到 pf_strategy:<handle> 标记
recordIDs  = append(recordIDs, pkg.StrategyID)                                          // 记录/报告拿到 custom:<variant>
if pkg.Form == CustomStrategyFormJS { codePackages = append(codePackages, *pkg) }      // 代码包走 code 通道
else                                { packages     = append(packages, *pkg) }         // 文本包走 text 通道
```

引擎侧（`nativeRedteam.ts:1419-1426`）唯一能把 `pf_strategy:<handle>` 换成 `custom:<variant>` 的地方是文本通道：

```ts
const requestStrategies = [
  ...applyCustomStrategyRefs(request.strategies, resolveCustomStrategies(request.custom_strategies ?? [])),
  ...materializedCodeStrategies.map((item) => ({ id: item.ref })),   // ← 代码包只贡献 file:// ref
];
const native = resolveNativeStrategies(requestStrategies, allowedFileRefs);
```

代码包的 `custom_strategies` 是**空数组**（它被分流到 `custom_strategy_code`），于是标记原样存活，`resolveNativeStrategies` 既不认 `file://`（不在本次物化集合）、也不认 `pf_strategy:` 前缀，也不在 promptfoo 的原生 id 集合里 → `native_generation_strategy_unknown`。

一句话：**代码通道给了引擎源码和 `file://` 引用，却没人把请求里的 `pf_strategy:` 标记换成对应 id。**

### 4.2 第二个独立缺口：向导路径根本没下发源码

`internal/api/handler/engine_run.go:606-613` 组装 `EngineRunRequest` 时只带：

```go
CustomPlugins:    customPlugins,
CustomStrategies: customStrategies,
// 缺 CustomStrategyCode
```

而确认路径（`promptfoo_engine_bridge.go:404-406`）带上了 `CustomStrategyCode: customStrategyCode`。这正是 P10/P11 那条老教训（“两条入口必须走同一个解析结果”）在新通道上重演：即使 4.1 修好，向导路径仍会因为「没有源码可物化」而失败（`custom:<variant>` 缺 `strategyText`/模块）。

### 4.3 修法建议（本轮零代码修改）

1. **让标记在代码通道也能被替换**（二选一）：
   - BFF：代码包的 `engineRefs` 直接发 `custom:<variant>`（它本来就是 promptfoo 认得的 custom id），而不是 `pf_strategy:<handle>`；
   - 或引擎：`applyCustomStrategyRefs` 同时吃 `custom_strategy_code` 表（条目里已有 `strategy_id`）。
2. **向导路径补上 `CustomStrategyCode`**：`engine_run.go` 的 `EngineRunRequest` 增加该字段，值取 `resolved.CustomStrategyCode`（解析函数已经返回它，只是没被用）。
3. **加一条端到端守卫**：现有单测覆盖了 BFF 分流与引擎物化，但**没有一条用例把「BFF 解析结果 → 引擎请求 → 引擎校验通过」串起来**；建议照 P10 的做法，在 `prepare + engine` 边界上断言「代码包的 id 在最终 `requestStrategies` 里存在」，否则这类“两段各自正确、拼起来不通”的缺陷还会再出现。
4. 小瑕疵：开关关闭时引擎返回 **409**、BFF 却返回 **400**（同一个 `code_strategy_disabled`）；对“本部署未开放该能力”语义，409/403 更贴切。
