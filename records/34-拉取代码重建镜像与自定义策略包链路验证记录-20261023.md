### 4.3 ❌ C：执行链路（本轮核心发现，P1 × 2）

**现象**：企业侧两条路都失败，错误同为 `native_generation_strategy_unknown`（既不是 promptfoo 的策略，也不是平台映射的 id）：

| 路径 | run | 失败形态 |
|---|---|---|
| 向导 API（`strategies=[{id:"pf_strategy:<handle>"}]`） | `er-10a185d5` | run 记录存**裸标记**（违反「记录存解析后 id」规则）→ 引擎拒绝 |
| 计划卡 confirm（P10 抽取器/双形态 refs 均正常出卡） | `er-c1fcb637` | 解析正确：记录存 `custom:p13-----------v2`、包随请求下发 → **引擎仍拒绝** |

**根因定位（代码级，两处独立缺陷）**：

1. **BFF 向导路径没接 pf_* 解析（P1）**：`engine_confirm` 走 `RedteamToolBridge.PreparePromptfooEngineRun`（有 `resolveCustomStrategies` + `CustomStrategies` 附加）；而 `internal/api/handler/engine_run.go` 的向导 handler **直接透传 strategies**，全文件无任何 `IsCustomStrategyRef`/解析/`CustomStrategies` 代码。P10 只在向导**前端下拉**并入「专家发布」分组，后端这条路没接。
2. **引擎前置校验先于包内联（P1）**：`promptfoo_engine/src/runner/nativeRedteam.ts` `executeNativeRedteamRun` 中 `resolveNativeStrategies(request.strategies)`（~L1281，词汇表校验，未认识 id 即 throw）跑在配置构建器的 `applyCustomStrategyRefs(strategies, resolveCustomStrategies(input.customStrategies))`（~L1073，把 `pf_strategy:` 标记换成 `custom:<variant>` + 内联 config）**之前**。标记在校验时还是裸的 → 必然 UNKNOWN。计划卡路径即使一切正确（实测包已随请求下发）也过不了这道门。源码注释自己写着「a config document still carrying a pf_strategy: marker would be a validateStrategies() throw mid-run」——但前置校验比它更早命中。

**修复建议**（未动代码）：
- 引擎侧：`executeNativeRedteamRun` 的词汇表校验应先做 `applyCustomStrategyRefs` 替换（或在 `resolveNativeStrategies` 里跳过 `pf_strategy:`/`promptfoo-custom:` 前缀标记，由配置构建器负责其存在性）；
- BFF 侧：向导 handler 复用 bridge 的解析 seam（或至少对 `pf_*` ref 提前拒绝并提示走计划卡），保证「记录存解析后 id」的既有规则；
- 回归守卫：补一条「计划卡 → confirm → 含自定义策略的 run 端到端」用例——现有测试只覆盖 `applyCustomStrategyRefs` 单元与 BFF 解析层，两端各自绿、链路红，正是「守卫在错误的缝上」的老形态。
