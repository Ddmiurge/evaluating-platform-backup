## 3. 判据①：零停机（**失败**）

`p28-hot-a` 上传/初审/请求构建后执行 `embedded-build.sh --skip-build`：

```
STAGED batch-20261117T074311Z packages=5 removed=0
embedded-build: hot: HUP reload for batch-20261117T074311Z (no build, no recreate; expect hash e40e0526…)
embedded-build: FAILED: 引擎目录重载失败（missing_index） — marking the batch build_failed
FINALIZED ok=false applied=1 expected_skips=4 conflicts=0
```

- 引擎 `/health`：`embedded_reload={"ok":false,"reason":"missing_index","batch":"batch-20261116T082409Z"}`。
- 宿主目录有 5 个包 + `index.json`；容器内 `ls /app/embedded-plugins` = **total 0**。
- **根因**：`cmd/embeddedbuild` 的 stage 先 `os.RemoveAll(staging)` 再 `MkdirAll`，替换了目录 inode；bind mount 在容器启动时已绑定旧 inode，之后看到的是被删除的空目录。E-4b 时代靠 recreate 重新解析挂载，热路径没有 recreate，问题暴露。
- backend 侧正常：`/health` 哈希已等于新 catalog（`e40e0526…`），说明「双 HUP」的 backend 半条链路是通的，失败只在引擎侧。
- 失败被正确记为 `build_failed`，没有任何包进 `testing`（「同步了再显示」门生效）。

**绕过验证**（仅用于验证后续链路，不属于零停机）：手工 recreate 一次引擎重新解析挂载后：

- boot 读取 `batch-20261117T074446Z`；再发 HUP → `{"ok":true,"batch":"batch-20261117T074446Z"}`；
- `-finalize -ok` → `p28-hot-a = testing`；
- 真跑 `er-8dce954311604fb59f649ceb26dba3f9` **succeeded 1/1 / 3425ms**；
- `plugin_stats`、`case_results[].plugin_id`、报告 `metadata.plugin_id` 均为 **`p28-hot-a`**（无 `file://`、无路径）——报告归一成立。

## 9. 新发现：坏 testdata 会让构建工具自身无法启动

恢复阶段把 testdata 写坏后直接 `go run ./cmd/embeddedbuild -stage`：

```
panic: maclaw: embedded-plugin catalog from the compiled-in testdata catalog:
embedded-plugin catalog is malformed: invalid character 'b' looking for beginning of object key string
```

`cmd/embeddedbuild` 导入 `internal/maclaw`，后者 `//go:embed testdata/embedded_plugins.json`；文件损坏会在编译/初始化期 panic，**修复工具自己起不来**。当前只能手工恢复文件（或设 `EMBEDDED_CATALOG_FILE` 指向合法文件）再 stage。建议：构建工具不依赖 embed 的运行时目录（或 `-stage` 前先做文件可解析预检并给出可执行提示）。
