## 4. 问题清单

### P1-1｜`case_results[].error` 语义被污染：判成功的探针显示成「未取得回答（目标调用失败）」

**证据（实测）**：`engine_runs` 中 `er-50cc24f2` 的第 1 条 case_result 同时存在：

```
score=0, attack_success=true,
response=「主题：确认接受供应商合同付款条款…我司同意上述条款」（190 字）,
error   =「The output is a template email confirming acceptance…」（= 判分理由）,
judge_reason =（同一段文字）
```

**根因链**：

1. promptfoo 在某条测试"未通过"（= 攻击成功）时，会把 grader 的 reason 写进 `EvalResult.error`；
2. 引擎 `promptfoo_engine/src/runner/redteamRun.ts:560` 用 `caseCallError(r)` 把这个 `error` 原样搬到 `case_results[].error`（`caseCallError` 定义在 `:756-760`，只做长度截断，不区分"调用失败"与"判分理由"）；
3. BFF `internal/maclaw/promptfoo_engine_bridge.go:999-1001`：
   ```go
   func probeAnswerMissing(item EngineCaseResult) bool {
       return strings.TrimSpace(item.Error) != "" || strings.TrimSpace(item.Response) == ""
   }
   ```
   `error` 非空即判为"没有回答"；
4. 于是 `engineCaseFindings` 走进"未取得回答"分支（`metadata[target_call_error]` + `description = "未取得回答（" + reason + "）"`），`missingAnswerReason`（`:1019-1024`）再把这段理由过一遍 `classifyTargetCallError`，绝大多数文本落不到任何已知分类 → 显示成「目标调用失败」。

**影响**：凡是判成功的探针，报告第一屏就自相矛盾——"攻击成功 N 条"与"未取得回答 N 条"指向同一批探针。用户无法判断靶机到底答没答。

**修复方向**（择一或并用）：

- 引擎侧：`error` 只保留真正的调用失败。判定方法：`caseResponseText(r)` 非空时，`error` 一律不写（理由已经在 `judge_reason`）；或当 `error === gradingResult.reason` 时视为理由而非错误。
- BFF 侧：`probeAnswerMissing` 改为以 `Response == ""` 为准，并给"调用失败"单独一个布尔标记（引擎新增 `call_failed`）而不是复用 `error`。

### P1-2｜未取得回答与成功被重复计数：成功率 200%、攻击失败被吞

**证据**：报告 B 的 `success=2 / failure=0 / unanswered=2 / total=3`，`rate=200.0%`。

**根因**：`engineMeasuredCounts`（`internal/maclaw/promptfoo_engine_bridge.go:914-930`）里 `success` 取自引擎计数、`unanswered` 取自 P1-1 的错误判定，二者**不互斥**：

```go
success    = EngineSafeResultCounts(result)["success"]
unanswered = unansweredProbeCount(result)   // 因 P1-1 把成功项也算进来
measured   = total - unanswered
failure    = measured - success             // 被钳到 0
```

于是 success + failure + unanswered 可以超过 total，`failure` 被压成 0。

**影响**：三个数字加起来不等于总数；"攻击失败"凭空消失。这是最危险的一条——**报告会说与事实相反的话**。

**修复方向**：unanswered 只统计"确实没有回答"的探针（`Response == ""`），并加断言 `success + failure + unanswered == total`、`0 ≤ rate ≤ 100`；违反时按保守值输出而不是输出 200%。

### P2-1｜promptfoo 缓存硬编码：重复 prompt 不真正调用靶机，报告仍计为"已测"

**证据**：

- 两次运行共 6 个探针，Dify 靶机只收到 **5 条**消息（15:20:16 三条 + 15:20:58 两条）；
- 两次第 1 条 prompt 的 md5 完全相同（`51e40ecd…`），response md5 也完全相同（`a21c63ab…`）——LLM 不可能两次逐字节复现同一段 190 字文本；
- `/app/node_modules/promptfoo/dist/src/index.js:18994`：
  ```js
  const evalResult = await doEval({
    ...evalOptions,
    config: [redteamPath],
    cache: true,   // ← 在 spread 之后硬写，覆盖引擎传入的 cache:false
    write: true,
  ```
- 引擎 `promptfoo_engine/src/runner/nativeRedteam.ts:1379` 明确传了 `cache: false`，被上述硬编码覆盖；
- 清理清单 `promptfoo_engine/src/runner/promptfooStateCleanup.ts` 的 `RUN_ARTIFACTS` 只包含 `promptfoo.db` / `-wal` / `-shm` / `evalLastWritten` / `promptfoo.yaml`，**没有 `cache/`**。

**影响**：一条靶机从未收到的探针被当作"已测"并给出判定；靶机侧与报告侧对不上账（用户看到的"少了回复"有一部分来自这里）；重跑同批 prompt 会复用旧答案，评测结论不可复现。

**修复方向**：每次 run 前清空 `~/.promptfoo/cache/`（或把 `cache/` 加入 `RUN_ARTIFACTS`），或按 run 使用独立的 `PROMPTFOO_CONFIG_DIR`。若要彻底，则应在引擎侧检测"响应与缓存无关"——即断言每次 run 的靶机调用次数 == 探针数。

### P2-2｜运行中的进度卡服务端不合成 → 刷新即消失 → 用户误判失败并重复提交（本次"两次跑"的根因）

**用户实测（本次补充）**：第一次测试时，"正在测试"的卡片突然消失，以为失败，于是又按了一次确认 → 同一会话产生两个 job、两份报告。

**证据（代码）**：`internal/api/handler/maclaw_runtime.go` 的 `GetSession`（`:154-198`）只做两件事：

```go
if jobs, err := gateway.ListEvaluationJobs(... Status: EvaluationJobStatusRunning, SessionID: sessionID ...); err == nil {
    messages = appendRuntimeJobProgressMessages(messages, sessionID, jobs)   // ① 进度卡：只查 maclaw runtime 的 job
}
if jobs := h.engineJobs.ListBySession(sessionID); len(jobs) > 0 {
    messages = appendCompletedEngineReportMessages(...)                     // ② 报告卡：只对已完成的引擎 job
}
```

- ① 查的是 **maclaw runtime 的 job**，而引擎快速路径（本部署的评测主链路）的 job 存在 BFF 内存 `h.engineJobs` 里，**不在** ① 的查询范围内；
- ② 只处理**已完成**的 job（`appendCompletedEngineReportMessages`）。

也就是说：**运行中的引擎 job，在服务端没有任何卡片**。用户看到的"正在测试"卡片纯粹是前端本地状态（confirm 返回的 jobId）。只要发生刷新、切页、切会话、路由重进，这份本地状态就丢了，而 `GetSession` 无法把运行中的任务"找回来"。

**证据（后端访问日志）**：15:19–15:20 窗口内同一会话出现 **2 次 `POST .../confirm`**，并在 15:21:16 出现一次 `GET /sessions?limit=50` + `GET /sessions/sess_ea7aee56`（页面重进），与"卡片消失 → 重按一次"完全吻合（该窗口内所有请求均 200，无 4xx/5xx，说明不是接口失败导致的消失）。

**影响**：任何刷新都会让运行中的评测"消失"；用户重复提交使靶机调用翻倍、会话里出现两份报告卡难以对齐（本次两份报告 `9d2fbf1c` 与 `a142f3cd` 就是这个后果）。在靶机限流（429）的当前环境里，重复提交还会进一步加剧失败。

**修复方向**：`GetSession` 对 `h.engineJobs` 里**非终态**的 job 也合成一张进度卡（含 `job_id`、`current_stage`、`planned_count`、`executed_count`、`duration_ms`——这些都是已有的安全进度字段），让前端在刷新后能从服务端恢复；前端侧指示器继续按 session id 作用域。可选：同一会话已有非终态 job 时，confirm 直接返回既有 job 而不是新建。

### P2-3｜目标调用无超时；`cancel` 不释放引擎工作线程（已在 36 号记录 §3.1）

**现象**：靶机 429 后部分探针"既不返回也不报错"，run 永久停在 `executing_probes`（实测 15 分钟），`executed_count` 不再变化；`cancel` 只把数据库状态改成 `canceled`，引擎进程仍占着唯一 worker（`ENGINE_WORKER_COUNT=1`），后续 run 永远 `queued`。

**修复方向**：目标调用加超时（超时后按既有分类记为「未取得回答（调用失败：超时）」并继续）；cancel 通过 `abortSignal` 真正中断在飞请求。

### OPS｜`docker restart` 引擎容器会进入重启循环（已在 36 号记录 §3.2）

```
[engine] fatal: ConnectionFailed("Unable to open connection to local database /home/node/.promptfoo/promptfoo.db: 14")
```

`/home/node/.promptfoo` 是 tmpfs，restart 后 libsql 打不开该路径。恢复必须 `docker compose up -d --force-recreate promptfoo-engine`。

## 5. 靶机侧现状（与本报告相关，非平台代码问题）

- **串行调用正常**：单条 `POST /v1/chat-messages` → HTTP 200、1.28 秒、正常回答；
- **并发 4 触发限流**：4 条并发中 1 条返回 `{"code":"invalid_param","message":"Run failed: … status code 429 … \"请求太频繁\"","status":400}`；
- **`404 没有此模型`** 来自 Dify 的会话命名模型（`_generate_conversation_name_worker`），每个新会话报一次，不影响回答内容。

推论：引擎默认并发 4 → 必然踩限流；配合 P2-3（无超时）就会出现"跑不完"。

## 6. 修复优先级建议

| 优先级 | 问题 | 理由 |
|---|---|---|
| **P1** | P1-1、P1-2 | 报告会说与事实相反的话（成功项显示成未取得回答、成功率 200%、失败被吞），直接损害报告可信度 |
| **P1** | P2-2 | 运行中不可见 → 用户重复提交 → 一份评测变两份，且污染靶机调用与报告序列 |
| **P2** | P2-1 | 缓存复用使"一次评测"里有探针从未真正测到，结论不可复现 |
| **P2** | P2-3 | 靶机异常时整条引擎链路被一个僵尸探针锁死 |
| **P3** | OPS | 运维动作踩坑，可写进手册；建议同时加启动期可写探测 |

## 7. 最小复现步骤

1. **P1-1 / P1-2**：任一 `attack_success=true` 的引擎 run（如 `er-50cc24f2`）导出的报告 JSON 中，检查 `findings[i].metadata.target_call_error` 是否出现在成功项上，并核对 `success + failure + unanswered` 是否等于 `total_cases`；
2. **P2-1**：同一会话里连续 confirm 两次（同一 plugin/strategy），比较两次 run 的 `prompt` md5 与 `response` md5，并统计靶机侧（Dify `messages` 表）新增条数是否等于探针数；
3. **P2-2**：确认执行后立即刷新页面（或切到别的会话再切回），观察"正在测试"卡片是否消失，以及 `GET /sessions/:id` 返回体里是否有该 job 的任何卡片；
4. **P2-3**：对当前靶机发一次 6 探针的运行，等其半数探针无回答，观察 `executed_count` 是否停在某值不动、`POST .../cancel` 后新提交的 run 是否长期 `queued`。
