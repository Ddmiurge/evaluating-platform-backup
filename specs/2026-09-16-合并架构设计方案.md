## 1. 合并后目标架构总图

```
┌─────────────────────────────────────────────────────────────────────────────┐

│  Agent 编排：          │   │  ┌────────────────────────────────────────────┐ │

                            │  └────────────────────────────────────────────┘ │

                            └───────┬──────────────────────────────────────────┘

┌───────────────────────────────────▼──────────────────────────────────────────┐
│ 被测模型（企业 LLM：OpenAI 兼容 / HTTP / WebSocket / 浏览器自动化 / 各家 SDK）     │
└────────────────────────────────────────────────────────────────────────────────┘
```

数据流（新链路）：

```
企业用户 → BFF → MaClaw 对话澄清 → plan_confirm（含插件/策略选择）
→ BFF 物化资源（target config 解密 + Skill payload handles + 专家样本模板）
→ BFF 调 promptfoo-engine 任务 API（redteam config JSON + 一次性凭据）
→ 引擎：synthesize（插件生成+策略变换）→ evaluate（调被测模型+GRADERS 判分）
→ 引擎回调 BFF：progress（计数/阶段）+ 结果（安全摘要，经引擎适配层脱敏）
→ BFF 判分裁决（judge_mode 融合，见 §5.4）→ 存 maclaw_redteam_evidence/reports → PDF 报告
```

两条链路并存：**Skill 链路（既有）与 promptfoo 链路（新）**，由 MaClaw 计划卡按能力类型选择，互不破坏。

## 2. 是否需要重构：逐项裁决

| 模块 | 裁决 | 理由 |
|---|---|---|
| 评估平台 Go 后端 | **保留 + 扩展** | BFF/多租户/计费/加密是平台核心价值；仅新增 promptfoo_engine_client 防腐层 + engine handler + 若干表。`internal/maclaw` 既有 9 工具不动 |
| 评估平台前端 | **保留 + 扩展** | 三门户结构不动；企业门户新增引擎向导/结果页，专家门户新增插件发布页（antd 组件重写，不搬 pf 的 React 代码） |
| MaClawSrv 编排层 | **保留（不动）** | 它仍是"大脑"——对话澄清、计划、工具选择。promptfoo 不替代其 agent loop，只是扩大可选工具面 |
| 既有 redteam_tool_bridge 9 工具 | **保留** | Skill 链路（CCBOS/AutoDAN 等）继续走它；它是平台安全边界（handle 化/脱敏）的既有实现 |
| 既有 judge（规则+CC-BOS LLM 阈值） | **保留为默认 judge_mode** | 产品语义（中文报告、安全分、judge profile）已稳定；作为基线与 pf grader 双轨（§5.4） |
| promptfoo 核心库（redteam/providers/matchers/commands） | **服务级引入（fork 锁版本）** | "继承所有能力"的唯一现实路径：40+ 插件、30+ 策略、89 provider、grader 族以库形态整体获得 |
| promptfoo Web UI（src/app） | **不直接引入，参考重写** | 技术栈不同（zustand/radix vs antd），且 pf UI 无多租户/权限概念；交互模式（setup 向导、report 视图）作为二阶段前端设计蓝本 |
| promptfoo CLI 入口（main.ts/entrypoint） | **废弃** | 平台以库 API（doRedteamRun/synthesize/evaluate）编程调用，不暴露 CLI |
| promptfoo server（src/server） | **废弃，由自研引擎适配层替代** | pf server 是单用户本地工具（无鉴权/无租户），企业化必须自建任务 API |
| promptfoo telemetry/share/cloud | **废弃并程序级关闭** | 数据外发风险；PROMPTFOO_DISABLE_REMOTE_GENERATION 等开关 + 构建期裁剪 |
| promptfoo remote generation 云依赖 | **改造**：自托管生成端点或强制本地 | unaligned harmful 插件依赖远端；企业内网需自建 PROMPTFOO_REMOTE_GENERATION_URL 端点（可选阶段） |

**总结论：不需要重构评估平台，需要"增厚"**。平台现有架构（BFF+防腐层+MCP bridge）恰好为嵌入第二执行引擎预留了模式——promptfoo 以"第九个容器 + 第二防腐层"进入，对既有代码是加法而非改写。

## 3. 关键设计决策

### 决策 1：promptfoo 如何嵌入 Go 技术栈

| 候选 | 思路 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 独立微服务（compose 新容器） | Node 24 容器跑引擎适配层 + promptfoo 库，对 BFF 暴露 REST | 隔离最彻底；语言栈解耦；可独立扩缩容；升级/回滚独立；库 API 可编程嵌入（doRedteamRun 已支持 logCallback/abortSignal） | 多一个容器运维；跨语言调用需适配层 | ✅ **推荐** |
| B. sidecar（每租户/每任务一个短命进程） | BFF 按需 spawn npx promptfoo 子进程，stdio/文件交换 | 天然租户隔离 | 进程冷启动慢（Node+TS 加载秒级）；pf 库按进程初始化（cliState/basePath 全局态）不适配高并发 spawn；凭据经环境变量传递面大 | ❌ |
| C. Go 子进程常驻池 | Go 管理常驻 Node worker 池 | 复用进程 | 需自研 IPC 协议+池管理；pf 进程内全局状态（cliState）要求每 worker 单任务串行，池意义有限 | ❌ |
| D. 渐进式 Go 重写核心 | 用 Go 重写插件/策略/判定 | 统一技术栈 | **与"继承 promptfoo 所有能力"直接冲突**：40+ 插件+89 provider 重写工作量以年计，且永远滞后上游；放弃 npm 生态（各家 SDK） | ❌（除非未来某天放弃"全量继承"目标） |

**选 A 的理由**：诉求是"继承所有能力"，只有整库引入能做到；容器化与平台既有 compose 编排同构（七容器→八容器）；引擎适配层是唯一自研 TS 代码面，可控制在薄壳范围。Node 全局态（cliState）问题通过"每任务独立工作目录 + 单进程内串行队列或按并发度开 worker"解决（见风险表 R1）。

### 决策 2：与 MaClawSrv agent 编排的关系

| 候选 | 思路 | 结论 |
|---|---|---|
| A. promptfoo 能力作为 MaClaw 的 MCP 工具暴露 | 平台注册新的粗粒度 MCP 工具（如 search_redteam_plugins / run_promptfoo_evaluation），MaClaw 在计划卡中选择"引擎能力"，BFF 转发引擎执行 | ✅ **推荐（A+B 混合）** |
| B. promptfoo agent 替代部分 MaClaw 职责 | 让 pf 的 jailbreak:meta/hydra 等攻击 agent 直接承担攻击规划 | ✅ 作为引擎内部实现细节吸收（攻击 agent 属于"执行"层，不碰"业务决策"层） |
| C. 双引擎并行供用户选择 | UI 上让用户选 MaClaw 链路或 promptfoo 链路 | ❌ 不做显式"选引擎"——用户选择的是**能力**（插件/策略），路由由 MaClaw 计划卡+BFF 决定 |

**裁决**：MaClaw 仍是唯一"业务大脑"（对话澄清、风险评估、计划编排）；promptfoo 是"执行引擎之一"。具体暴露 3 个新 MCP 工具给 MaClaw：`search_redteam_plugin_catalog`（检索 pf 插件/策略，对接 capability_catalog.go 既有模式）、`run_promptfoo_redteam_evaluation`（组合生成+执行+判分）、`get_promptfoo_evaluation_result`（安全摘要查询）。**这回答了 AGENTS.md 红线**：评测引擎语义从"唯一在 MaClawSrv"演进为"决策在 MaClawSrv，确定性执行在平台侧工具层，promptfoo 是工具层新增的执行引擎"——平台仓库仍然不自己实现引擎代码，只是引入引擎服务（红线禁止的是"重新引入/重新实现"，不是"以服务形态扩展工具层"）。**此点列入待确认问题 Q1。**

### 决策 3：插件生态如何暴露

**推荐：三级递进。**

1. **Phase 1（内置目录）**：pf 40+ 插件/30+ 策略全部映射进平台 capability catalog（`capability_catalog.go` 既有模式），企业用户在计划确认时由 MaClaw 检索推荐，无需前端改造。
2. **Phase 2（专家发布自定义插件）**：专家门户新增"插件包发布"——对应 pf 的 custom plugin（yaml：generator+grader）、file:// strategy（JS）、自定义 provider 三形态，存储进 `maclaw_resources`（加密）+ Hub 分发（复用 skill_publications/shadows 机制，新增 resource_kind='pf_plugin'）。企业租户安装后，引擎任务以挂载卷/上传方式注入自定义包。
3. **Phase 3（与 Skill 体系关系）**：Skill 与 pf 插件**并存不合并**——Skill 输出 payload_dataset（确定性攻击资产），pf 插件输出 TestCase（LLM 生成+判定成对）。长期可用"pf custom plugin 包装 Skill"打通（Skill 作为静态生成器），列为远期可选，不在本阶段承诺。

**不推荐**让企业用户直接编辑 pf yaml（专家/企业角色分离是平台既有治理模型）。

### 决策 4：判定系统融合

| 候选 | 思路 | 结论 |
|---|---|---|
| A. pf grader 全量替代平台 judge | 引擎内判完直接回结果 | ❌ 破坏中文报告/安全分/零成功=100 分等产品语义，且 pf 判定 rubric 为英文 |
| B. 平台 judge 判定 pf 产物 | pf 只生成+执行，判分全走平台 judge | ❌ 丢失 pf grader 与插件的配对语义（每插件专用 rubric），PII/SQL 注入等结构性漏洞判不准 |
| C. 双轨 + 裁决层 | judge_mode 扩展枚举：`auto`（既有）/`promptfoo_native`（pf grader 原生判定）/`platform_rejudge`（pf 执行+平台 CC-BOS 复判） | ✅ **推荐** |

**C 细节**：`promptfoo_native` 模式下引擎返回 `{pass, score, severity, confidence, reason(脱敏)}`；BFF 增加映射器把 pf 的 pass/severity 映射进平台 attack 结果语义（success=pass==false 即"攻击成功=模型未通过安全断言"——注意**极性相反**：pf 的 fail=漏洞被证实=平台攻击 success，映射器必须显式翻转并写测试）；`platform_rejudge` 模式用于对照审计与回归期数据一致性校验。报告层两轨结果分列展示，安全分以所选 judge_mode 为准。

### 决策 5：数据模型融合

**原则：pf 的 test/result/evaluation 是引擎运行期临时态，平台表是唯一持久层。**

| pf 概念 | 平台落点 |
|---|---|
| TestCase（vars/assert/metadata.pluginId） | 不持久化原文；生成态留在引擎工作目录（任务结束清理），安全摘要进 evidence |
| Eval / EvalResult（prompt/output/score） | 逐条映射为 `maclaw_redteam_evidence` 行（含 judge_mode、plugin_id、strategy_id、pf pass/score/severity 映射后的平台结果语义、脱敏 reason 摘要） |
| Evaluation 汇总（统计） | `maclaw_redteam_reports` 一行（新增 engine='promptfoo'、plugin 维度统计 JSON、token 用量） |
| 自定义插件包 | `maclaw_resources` 新 resource_kind；发布记录复用 `maclaw_skill_publications`（加 kind 字段或并行表） |

**浏览器红线不变**：引擎产物含 prompt/response 原文，允许存在于引擎容器内存/临时目录，**永不进入平台 API 响应**；回写平台的只有 handle+摘要+计数（引擎适配层脱敏回调，与 bridge 的 safeJudgeScoreMetadata/safeErrorSummary 同一纪律，redteam_tool_bridge.go:1767/1704 既有模式）。

### 决策 6：前端融合方向（概述，详细二阶段）

- **不嵌入 pf Web UI**（iframe 或微前端都不做）：无租户/权限模型、样式体系（tailwind/radix）与平台（antd 6 白主题）割裂。
- **对话优先（v2，Q3 已裁决）**：聊天工作台（AI 服务，菜单加「推荐」徽标）为推荐主链路；企业门户另增两页作为辅助入口：**自选评测向导**（原"红队引擎向导"，菜单名「自选评测」；参考 pf setup 向导信息架构：这次要测什么→检测项与攻击策略→被测模型连接→预估→运行，antd 实现；页首置「推荐用 AI 对话」引导条+跳转按钮）、**评测报告页**（原"引擎结果页"，菜单名「评测报告"；参考 pf report 的风险类别/severity/策略统计视图）。
- 专家门户插件发布页参考 pf 的 custom plugin 三形态表单。
- 复用平台既有 SSE 进度卡与报告卡组件（ChatCards/jobProgressMessages）；聊天页被测模型配置 Drawer 为既有交互，两条链路共用。

## 4. 实施路线图

### Phase 0：引擎服务骨架（改动最小闭环）

- **目标**：promptfoo 以第八容器跑起来，BFF 能发起一次编程式红队 run 并拿到脱敏结果。
- **改动**：新目录 `evaluating_platform/promptfoo_engine/`（引擎适配层 TS 薄壳 + Dockerfile）；backend 新增 `internal/maclaw/promptfoo_engine_client.go`（新防腐层单元）+ 任务 API handler；compose 增 service；环境变量：`PROMPTFOO_DISABLE_REMOTE_GENERATION=1`、`PROMPTFOO_DISABLE_TELEMETRY`、`PROMPTFOO_DISABLE_SHARE`。
- **交付物**：`POST /api/v1/engine/redteam/run`（管理员可用）端到端跑通一个内置插件（如 pii）对 OpenAI 兼容目标。
- **验收**：compose 八容器 up；管理员发起 run→引擎日志可见 synthesize+evaluate→结果脱敏落 `maclaw_redteam_evidence`；浏览器侧无任何原文。
- **风险**：pf 库 API 的 Node 全局态（R1）；裁剪 telemetry 的构建期依赖。

### Phase 1：能力目录 + 计划卡路由

- **目标**：MaClaw 能检索 pf 插件/策略并纳入 plan_confirm；判定双轨落地。
- **改动**：capability_catalog 扩展（插件/策略元数据：id/描述/参数 schema/severity 映射）；bridge 新增 `search_redteam_plugin_catalog` / `run_promptfoo_redteam_evaluation` / `get_promptfoo_evaluation_result` 三工具；judge_mode 枚举扩展 + pf→平台结果映射器（含极性翻转，单元测试覆盖）；报告编译器支持 engine='promptfoo' 维度。
- **验收**：企业用户对话发起评测→计划卡出现 pf 能力→确认后走引擎链路→PDF 报告含插件维度统计；既有 Skill 链路回归全绿。
- **风险**：双判定结果不一致引发用户困惑（用报告分列缓解）。

### Phase 2：企业门户前端（详细设计见文档 3 v2）

- 自选评测向导页 + 评测报告列表/详情页（antd），SSE 进度接入既有组件；菜单名通俗化（自选评测/评测报告），「AI 服务」加推荐徽标，向导页页首引导回 AI 对话（对话优先）。
- **验收**：不进聊天工作台也能完成一次引擎评测；向导页对话优先引导（徽标+引导条+跳转按钮）在位。

### Phase 3：专家插件生态

- 专家门户插件包发布（三形态表单）→ maclaw_resources 加密存储 → Hub 分发 → 企业安装 → 引擎任务注入自定义包；引擎侧 file:// 加载的沙箱化（容器内只读挂载、禁网络出口除外白名单）。
- **验收**：专家发布一个 custom plugin（yaml）→ 企业租户安装 → run 中生效。
- **风险**：JS 策略/provider 任意代码执行的沙箱边界（R3，最重的安全项）。

### Phase 4（可选）：自托管攻击生成端点

- 内网部署生成服务对接 `PROMPTFOO_REMOTE_GENERATION_URL`，解锁 unaligned harmful 全类目；或长期维持禁用白名单。

## 5. 兼容性影响

| 链路 | 影响 | 说明 |
|---|---|---|
| 企业聊天主链路（SSE/plan_confirm/confirm run） | **不受影响** | 新能力只是计划卡可选项；既有 9 工具与 confirm 流程零改动 |
| Skill 分发链路（Hub/shadows/manage_skill） | **不受影响** | Skill 语义与执行路径原样；Phase 3 只是在同一资源存储里新增 kind |
