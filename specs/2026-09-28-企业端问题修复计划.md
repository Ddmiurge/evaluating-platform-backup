## 0. 背景与范围

企业门户当前有两条评测执行链路：

1. **AI 对话链路（主路径）**：聊天工作台 → MaClaw `plan_confirm` 卡 → 用户确认 → `evaluation.run` job → 平台红队 MCP bridge `execute_redteam_evaluation_batch` → 进度卡 → PDF 报告。
2. **自选评测链路（promptfoo 引擎，Phase 2）**：`/enterprise/eval` 页 → `POST /api/v1/maclaw/engine/runs` → `promptfoo-engine` 容器（方案 A：引擎侧 LLM 生成用例 + evaluate 模式执行 + llm-rubric 判定）→ 3s 轮询展示聚合结果。

本次企业端试用暴露 5 个问题（用户编号 1/2/3/5，其中问题 3 含两个子诉求，问题 4 编号被跳过）。总览见 §1，逐项方案见 §2。

**关键约束（贯穿所有改动）：**
- 浏览器/BFF 响应/SSE/job progress/report DTO **不得**出现：原始 prompt、原始目标响应、payload 正文、target secret、token、evidence content、本地路径。
- promptfoo 引擎 **fail-closed 开关不得放宽**（`PROMPTFOO_DISABLE_REMOTE_GENERATION` 等保持置位）。
- MaClaw 升级补丁点、`internal/maclaw` 防腐层边界不变；不 import MaClaw 源码。
- 前端改动必须过 `npm run build`；后端改动必须过 `go test ./...`；收尾 `git diff --check`。

## 2. 逐项详述

### P1 — 聊天窗口消息"跳出又撤销"来回抖动（P0，已确认）

**现象**：AI 对话中提交测试（确认执行计划）后，对面的聊天消息反复出现又消失，来回抖动。

**代码定位（候选根因，需运行复现确认）**：

抖动本质是**多个写入方并发修改同一份 `messages` 状态，且其中存在"全量替换"与"局部追加"互相覆盖**。涉及以下写入方：

1. `frontend/src/pages/enterprise/ChatPage.tsx`
   - `sendPrompt`：局部 `setMessages` 追加临时用户消息 + 占位助手消息。
   - `handleConfirmPlan`：`confirmPlan` 返回后局部 `setMessages` 追加进度卡。
   - `startRunStream`（SSE 通道）：每个 event `setMessages(prepareMessagesForDisplay([...previous.filter(id), eventMessage]))`。
   - `waitForEvaluationJob`（job 轮询通道，1s 一次）：`jobRunToStream` 有 run 时生成 `job-${jobId}-queued` 进度卡并 `setMessages`；succeeded 时 `applySessionSnapshot` **全量替换**。
   - `applySessionSnapshot`：`setMessages(prepareMessagesForDisplay(rawMessages, session))` —— **用服务端快照全量覆盖本地消息**。
   - `waitForAssistantReply`（1.5s 轮询）：每轮 `applySessionSnapshot` 全量替换。
2. `frontend/src/pages/enterprise/chatDisplay.ts`
   - `prepareMessagesForDisplay` = `collapseProgressMessages` + `markStalePlanMessages` + `syncPlanMessagesWithSession`。
   - `collapseProgressMessages` 按 `assessment_id` 折叠 progress 卡，只保留每个 `assessment_id` 的**最新一条**。
3. `frontend/src/services/maclawRuntime.ts`
   - `toEventChatMessage`：SSE 事件 → 消息，progress 卡 `id = maclaw-event:${type}:${runID}:${status}:${createdAt}`，`assessment_id = runID`。
   - `confirmPlan` / `jobRunToStream`：job 通道 progress 卡 `id = job-${jobId}-queued`，`assessment_id = progress.run_id`。

**最可能的根因（按概率排序）**：

- **R1（最可能）：SSE 流 与 job 轮询 双通道并发写 progress 卡，且 `assessment_id` 不一致导致折叠抖动。**
  SSE 通道用 `run_id` 作 `assessment_id`，job 轮询通道用 `progress.run_id`。两者若取值不同（例如 job 的 `progress.run_id` 尚未回填、或 run id 与 job 内部 run id 不同），`collapseProgressMessages` 会认为它们是**两条不同**的 progress 卡，交替成为"各自 assessment_id 的最新"，于是卡片 A/B 互相顶掉 → 视觉抖动。
- **R2：`applySessionSnapshot` 全量替换 与 局部追加 竞争。**
  确认执行后，`waitForEvaluationJob` 的 succeeded 分支 / `startRunStream` 的 onDone / `waitForAssistantReply` 都会调用 `applySessionSnapshot` 全量覆盖。若服务端快照此刻尚未持久化本地刚追加的进度卡/助手消息，全量替换会把它们抹掉（"撤销"）；下一轮快照补齐后又出现（"跳出"）。
- **R3：占位消息 id 不稳定。**
  `sendMessage` 在 run 未完成时返回占位消息 `id = maclaw-message-pending:${run?.id || Date.now()}`。`Date.now()` 兜底导致 id 每次不同，React `key` 变化触发重挂载，配合全量替换产生闪烁。

**排查步骤（编程 Agent 先做，再改）**：
1. 复现：企业账号 → 聊天 → 确认一个 `test_count=3` 的计划 → 打开 DevTools，在 `setMessages` 各调用点打 `console.log`（临时，提交前移除），记录每次 `messages` 数组长度、各消息 `id`/`assessment_id`/`card_type` 序列。
2. 对照 SSE 通道 progress 卡的 `assessment_id` 与 job 轮询通道 progress 卡的 `assessment_id` 是否一致。
3. 确认抖动窗口是否集中在"确认执行后 0~10s"（双通道并发期）。

**修复方向（择一或组合，需保持安全边界）**：
- **方案 A（推荐，治本）**：确认执行后**单一数据源**。以 job 轮询为唯一 progress 写入方，SSE 仅用于终态/报告事件；或反之。消除双通道对同一 progress 卡的并发写。
- **方案 B**：统一 `assessment_id`。SSE 与 job 通道 progress 卡都用同一个稳定键（如 `job.id` 或 `run.id`，二者取同一来源），使 `collapseProgressMessages` 能正确折叠为一条。
- **方案 C**：`applySessionSnapshot` 全量替换前做**合并**而非覆盖——保留本地已存在且服务端尚未返回的临时/进度消息（按 `id` 去重合并），避免抹掉刚追加的卡片。
- **方案 D**：占位消息 id 稳定化——`sendMessage` 占位消息 id 用 `run.id`（无 run 时用 `sessionId + 时间戳` 固定一次），避免 `Date.now()` 每次不同。

**验收标准**：
- 确认执行 `test_count=3` 的评测，聊天窗口 progress 卡**单调推进**（排队→执行→报告），无"出现→消失→再出现"抖动。
- 执行完成后稳定显示报告卡（风险等级 + 安全分 + 下载按钮），不再闪回。
- DevTools 中 `messages` 数组在稳定期长度不再周期性增减。
- `npm run build` 通过；`git diff --check` 干净。

### P2 — 自选评测插件/策略太少，希望与 promptfoo 对齐（P1）

**现状**：
- 前端 `frontend/src/services/engineEval.ts`：`ENGINE_PLUGIN_OPTIONS` 6 个（harmful/pii/prompt-injection/jailbreak/bias/security-exploit），`ENGINE_STRATEGY_OPTIONS` 4 个（direct/role-play/encoding/multi-turn）。
- 后端 `internal/maclaw/promptfoo_plugin_catalog.go`：同样 6 插件 + 4 策略（静态目录，供 MaClaw 发现 + 能力卡）。
- 引擎 `promptfoo_engine/src/runner/generateTests.ts`：方案 A 下，插件/策略只是**给生成 LLM 的分类标签**（`plugin_id`/`strategy_id`），由 LLM 自由生成用例，**不是 promptfoo 原生插件**。
- promptfoo 官方（v0.123.0 文档）：**157 个插件、6 大类**（Brand / Compliance & Legal / Dataset / Security & Access Control / Trust & Safety / Custom），并支持 NIST AI RMF、OWASP LLM Top 10、OWASP API、MITRE ATLAS、ISO 42001、GDPR、EU AI Act 等框架插件。

**核心矛盾（必须先向用户澄清，决定 P2 的"对齐"深度）**：

| 对齐深度 | 含义 | 是否触碰 fail-closed | 工作量 |
|---------|------|---------------------|--------|
| **L1 目录对齐（推荐）** | 把平台目录从 6 个扩充到覆盖 promptfoo 主要插件分类（按 6 大类组织），仍走方案 A（LLM 生成 + evaluate + llm-rubric）。插件 id 采用 promptfoo 命名（如 `harmful:cybercrime`、`jailbreak`、`pii`、`prompt-injection`、`bias`、`security-exploit`、`hallucination` 等）。 | 否 | 中 |
| **L2 原生插件** | 真正启用 promptfoo 原生插件生成（`redteam.run`）。 | **是**——原生插件生成被 `PROMPTFOO_DISABLE_REMOTE_GENERATION` 禁用，需放宽开关，与既定 fail-closed 决策直接冲突 | 高 + 安全决策 |

**建议**：默认做 **L1**（与 fail-closed 不冲突，纯目录/分类扩充）。L2 需用户明确接受"放宽远程生成开关、端点只指向平台 LLM"后才启动（见 `docs/architecture/promptfoo-generation-options.md` 方案 B）。

**L1 实施要点**：
1. 后端 `promptfoo_plugin_catalog.go`：按 promptfoo 6 大类扩充 `promptfooPluginCatalog`，每个条目带 `category`、`plugin_id`（对齐 promptfoo 命名）、`risk_types`、`default_severity`、`use_when`。建议首批覆盖高频安全类：
   - Trust & Safety：`harmful`（含 `harmful:cybercrime`、`harmful:illegal-activities`、`harmful:violent-crime` 等子项）、`jailbreak`、`bias`、`pii`
   - Security & Access Control：`prompt-injection`、`security-exploit`（含 SQL/SSRF/命令执行）、`ascii-smuggling`、`excessive-agency`
   - Brand：`hallucination`、`off-topic`、`competitors`
   - Compliance：按需（`coppa`/`ferpa` 等，可后置）
   - 策略：在现有 4 个基础上，可补充 promptfoo 常见策略（如 `crescendo`、`assumed-knowledge`、`few-shot`、`homoglyph`、`many-shot`、`obfuscation`、`translate` 等），但需与引擎生成 prompt 的 `strategy_id` 词表一致。
2. 前端 `engineEval.ts`：`ENGINE_PLUGIN_OPTIONS`/`ENGINE_STRATEGY_OPTIONS` 与后端目录**单一来源**对齐（建议后端提供 `GET /maclaw/engine/catalog` 返回目录，前端拉取，避免两处硬编码漂移）。至少先手动保持 id 一致。
3. 引擎 `generateTests.ts`：`plugin_id`/`strategy_id` 词表与目录一致；`inferSeverityFromPlugin`/`inferCategory`/`CATEGORY_PREFIXES` 需覆盖新增 id（否则新插件严重度/分类归入 `other`/`medium`）。
4. 表单分组：前端插件下拉按 6 大类分组（`Select` 的 `options` 用 `optGroup`），提升可读性。

**验收标准**：
- 自选评测页插件下拉覆盖 promptfoo 主要安全类（≥ 15 个插件、按类分组），策略 ≥ 8 个。
- 选中新插件（如 `harmful:cybercrime`）发起 `num_tests=3` 评测，引擎生成用例的 `plugin_id` 正确、结果 `plugin_stats`/`severity` 归类正确（非 `other`）。
- 后端 `go test ./...` 通过（catalog 新增条目有测试）；前端 `npm run build` 通过。
- fail-closed 开关全程未动（`PROMPTFOO_DISABLE_REMOTE_GENERATION=1` 等）。

### P3a — 攻击 Agent 是否需要自己再搭一个 Agent（决策/咨询）

**结论（给用户的答复）**：
- **不需要平台强制自建 Agent。** 被测 Agent 可以是用户**已有的**任何对外暴露的智能体（企业客服 Agent、内部 RAG Agent、MCP Agent 等），平台只负责"能连上去 + 能多轮对话 + 能判定"。
- 平台缺的不是"Agent 本体"，而是**连接 Agent 的协议适配**（见 P3b）。只要被测 Agent 提供一个可访问的对话端点（OpenAI Assistants API / 自定义 chat endpoint / MCP / 其他），配置进"智能体连接"即可作为被测目标。
- 若用户手上**没有**现成 Agent，才需要自己搭一个（用任意框架，如 LangChain/LlamaIndex/自研），再把它的端点接入平台。这是被测对象准备问题，不是平台功能缺口。

**需要在文档/产品层面明确的点**：
1. 平台支持的 Agent 协议范围（见 P3b 的协议选型）。
2. 多轮对话如何承载（Agent 通常有会话状态，攻击用例需按会话组织，与当前"单轮 prompt→响应"模型不同）。
3. Agent 的工具调用/副作用如何在评测中隔离（避免评测触发真实副作用，如发消息、改数据）——建议评测环境用 mock/沙箱端点。

**验收标准**：本节为决策说明，无代码验收。需在最终产品文档/帮助页写明"被测 Agent 准备指引"。

### P3b — 增加"智能体连接"配置窗口（P1）

**现状**：
- target 模型只有两种 kind：`llm` / `http`（`internal/maclaw/client.go` `EvaluationTargetKindLLM`/`EvaluationTargetKindHTTP`）。
- 前端 `ChatPage.tsx` 的"被测模型连接" Drawer 只有 LLM 表单（name/provider/base_url/model/api_key/supports_vision），`saveAndProbeTarget` 固定 `kind:'llm'`。
- 引擎/`call_evaluation_target` 只按 OpenAI-compatible `chat/completions` 单轮调用。

**目标**：让用户能配置一个**智能体（Agent）连接**，作为被测目标，支持多轮对话。

**方案（分阶段，控制范围）**：

**阶段 1（最小可用，推荐先做）**：新增 target `kind = "agent"`，复用现有加密 target 存储，扩展字段：
- `agent_endpoint`（对话端点 URL）
- `agent_protocol`：`openai_assistants` | `chat_completions_stateful` | `custom`（v1 建议先支持 `openai_assistants` 和"无状态 chat_completions"两种）
- `agent_id` / `assistant_id`（Assistants API 需要）
- `session_mode`：`single_turn` | `multi_turn`（多轮时引擎按会话组织用例）
- 复用 `credential_secret`（write-only）、`supports_vision`
- 前端 Drawer 增加"被测对象类型"切换（LLM / 智能体），智能体分支渲染 agent 字段。
- 后端 `GetTargetWithSecret` / `MaterializeEngineCredentials` 透传 agent 字段（不落日志/不回浏览器）。
- 引擎 `redteamRun.ts` / `generateTests.ts`：agent 目标按协议调用；多轮时把同一会话的多条用例串起来（需设计会话状态承载，v1 可先做单轮 agent，多轮标记为后续）。

**阶段 2（后续）**：MCP Agent 连接、Agent 工具调用 mock/沙箱、多轮攻击策略（crescendo 等）与 agent 会话绑定。

**安全边界**：
- agent 凭据同 target secret，write-only，只在服务端调用时使用。
- 评测不得触发 Agent 真实副作用；文档需提示用户用沙箱/mock 端点。
- 浏览器/报告/进度不出现 agent 配置 secret、原始对话内容。

**验收标准**：
- 前端"被测模型连接" Drawer 可切换 LLM / 智能体，智能体表单可保存并做连通性探测（`health-check` 适配 agent 端点）。
- 配置 agent 目标后，发起 `num_tests=3` 评测能成功调用 agent 端点并出结果（v1 单轮即可）。
- agent secret 不出现在任何浏览器响应/日志/`engine_runs` 表。
- 后端 `go test ./...`、前端 `npm run build` 通过。

### P5 — 攻击结果展示（逐条/明细）（P1）

**现状**：
- 聊天 `ReportCard`（`ChatCards.tsx`）：只显示 执行/成功/失败 计数 + 风险等级 + 安全分 + PDF 下载。**无逐条明细**。
- 自选评测 `EngineEvalPage.tsx`：显示 `plugin_stats`（按插件聚合）+ `severity_counts` + 拦截率。**无逐条明细**，且 `risk_categories`、`plugin_stats[].top_reasons` 字段后端已返回但前端未展示。
- 引擎 `SafeRunResult` 已含：`totals`、`severity_counts`、`risk_categories[]`（含 `plugins[].top_reasons` 脱敏原因）、`plugin_stats[]`、`strategy_stats[]`、`token_usage`。

**安全边界（关键约束）**：
- 平台**不向浏览器返回原始 prompt / 原始目标响应 / payload 正文**（BFF 安全边界，`maclaw-current-state.md`）。
- 因此"攻击结果展示"只能在**脱敏摘要**层面做：展示"哪类攻击、哪个插件/策略、严重度、脱敏后的原因摘要（≤200 字 redacted reason）"，**不展示**攻击原文和目标回答原文。
- 逐条"攻击成功样例"的完整内容仍留在 PDF 报告（服务端生成）与 evidence handle（服务端），前端只展示安全摘要 + 下载入口。

**方案**：
1. **自选评测页（改动小，先做）**：`EngineEvalPage.tsx` 结果区补充展示
   - `risk_categories`：按风险类别分组，每组展示 `count` + `severity_counts` + 组内 `plugins[].top_reasons`（脱敏原因，最多 3 条/插件）。
   - 攻击成功明细表：列出 `attack_success>0` 的插件/策略，附 `top_reasons` 脱敏摘要。
   - 明确标注"以下为脱敏摘要，完整内容见 PDF 报告"。
2. **聊天链路（改动中）**：`ReportCard` 增加"攻击成功摘要"折叠区，展示 `success_count` 条脱敏摘要（来自 report metadata 的安全字段）。需后端在 report 事件/DTO 中补充**安全**的 `findings_summary`（脱敏，不含原文）。
3. **后端**：确认 `SafeRunResult` 的 `top_reasons`/`risk_categories` 已脱敏（`promptfoo_engine/src/sanitize/redact.ts` `redactReason`）；聊天链路 report DTO 若需逐条摘要，需新增**脱敏**字段（复用 `redactReason`），**不得**带原文。

**验收标准**：
- 自选评测页在结果区展示风险类别分组 + 脱敏原因摘要 + 攻击成功明细（插件/策略/严重度）。
- 攻击成功 0 条时展示"未发现攻击成功"（与报告"最高安全"一致）。
- 前端展示的任何文本经 `redactReason` 脱敏，**不含**原始 prompt/响应/payload（抽查 + 代码审查确认无原文字段透传）。
- `engine_runs.result` 与 API 响应零泄漏（与既有安全抽查口径一致）。
